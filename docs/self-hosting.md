# Self-hosting ocra Cloud

A company GitLab with its own models, end to end: [gitlab.md](gitlab.md).

The same API and web app as [the hosted console](https://app.ocracloud.com/), on Node with Postgres or libSQL (a local SQLite file by default) instead of Cloudflare Workers and D1. The Node host in `src/node/` reads the client's address from the socket or a trusted proxy, counts rate limits in memory or in the database, runs scheduled maintenance, and serves `web/dist`. It can execute review jobs itself or use [remote runners](runner.md). CI tests the API on D1 and Postgres and runs Node-specific server tests.

## Run it

With Docker Compose on one machine: Postgres, the server, and Caddy in front of them ending TLS (`selfhost/`).

1. **Start.** From `selfhost/`:

   ```sh
   docker compose up -d
   ```

   Nothing needs filling in first. The first start makes the secrets (the master key, the session secret and Postgres's password, in the `secrets` and `db-password` volumes), a one-off `migrate` run applies the migrations, the server starts, then Caddy, once the server answers its health check. It answers at `https://localhost`; to serve another name, copy `.env.example` to `.env` and set `OCRA_DOMAIN` (and `OCRA_TLS`, below) before starting.

2. **Open the setup page.** Until someone can sign in, every page of the server is its setup page. It opens with the setup code the server prints in its log:

   ```sh
   docker compose logs ocra | grep setup_needed
   docker compose exec ocra node dist/setup-code.mjs   # at any time
   ```

   The code is made from the session secret: whoever can read the server's log or run a command in its container is its administrator. The page stays at `https://<OCRA_DOMAIN>/setup` after the first hour, behind the same code.

3. **Go through its steps.** Each one tests its connection with what is typed before it is saved, and says in plain words what failed and what to change:

   - **Network:** the company's certificate authority (PEM) and proxy, when GitLab, the sign-in provider or the model gateway sit behind them. The tests of the other steps go through them.
   - **Sign-in:** the company's OpenID Connect provider (issuer, client id and secret), with the redirect URI to register shown beside the fields, and who may sign in (Who may sign in).
   - **Code host:** a self-managed GitLab (its application and the review bot's token, [gitlab.md](gitlab.md)), or a GitHub App on github.com or a GitHub Enterprise Server.
   - **Models:** the company's model gateway (OpenAI chat completions or Anthropic messages), its key, and the model of each tier; the test lists the gateway's models and names any tier's model it does not list.
   - **Health:** every part tested as the server runs now (below).

   Saving keeps the settings in the database, secrets sealed under the master key. **Start again now** applies them: the server starts again in the same process, in a few seconds, and the page waits for it.

4. **Sign in** at `https://<OCRA_DOMAIN>`. Each account starts with the setup page's models until it saves its own on the Models page.

5. **Connect the CLI.** Each developer points the `ocra` CLI at this server and signs in once, confirming a code in the browser:

   ```sh
   export OCRA_CLOUD_URL=https://ocra.example.com
   ocra login
   ocra review     # in a repository with changes
   ```

   The review's model calls go through this server's gateway, metered and capped per account; the CLI never holds the model's key. To have a bot review every merge request, see [gitlab.md](gitlab.md).

A variable in the server's environment (`selfhost/ocra.env`, read when it exists, or the variables below) wins over the setup page, which then shows its field locked: settings that belong in configuration management stay there. A setting the page does not hold (email, Slack, metrics, limits) is a variable only. `MASTER_KEY_FILE`, `SESSION_SECRET_FILE` and any other `<NAME>_FILE` read `<NAME>` from a file, as Docker gives secrets.

`OCRA_TLS` says where the certificate comes from: `internal` (Caddy's own CA, the default, for a trial), an email for a public name that Let's Encrypt can reach, or `/certs/<cert>.pem /certs/<key>.pem` with the company's certificate placed in `selfhost/certs/`. With `internal`, browsers and the CLI trust the server only once they trust Caddy's root: export it with `docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt ocra-root.crt`, add it to the machine's trust store, and give it to the CLI as `NODE_EXTRA_CA_CERTS=ocra-root.crt` (without it, `ocra login` fails with `fetch failed`). Compose sets `PUBLIC_URL` and `TRUSTED_PROXY_HOPS` for you; when Caddy cannot have ports 80 and 443, set `OCRA_HTTP_PORT`, `OCRA_HTTPS_PORT` and `OCRA_PUBLIC_URL` in `.env`.

### Upgrades

```sh
./upgrade.sh
```

It asks whether to back up first (yes by default; `--yes` backs up without asking, `--no-backup` skips it), pulls the checkout's newest commit, builds the image, and runs `docker compose up -d --wait`: the `migrate` run applies the new migrations before the server starts again. The Health step then says whether every part answers.

### Backups

```sh
./backup.sh
```

writes `selfhost/backups/<UTC time>/`: `ocra.dump` (`pg_dump`) and `secrets.tar`, the `secrets` and `db-password` volumes. Keep both, and a copy somewhere else: the database's model and platform keys open only with that master key. To restore into a fresh deployment, start it once (`docker compose up -d`), then:

```sh
docker compose stop ocra
docker compose run --rm --no-deps -T secrets sh -c 'cd / && tar -xf -' < backups/<time>/secrets.tar
docker compose exec -T postgres pg_restore -U ocra -d ocra --clean --if-exists < backups/<time>/ocra.dump
docker compose restart postgres && docker compose up -d
```

Behind your own load balancer instead, run the image alone:

```sh
docker build -t ocra-cloud .
docker run -p 8787:8787 -v ocra-data:/data --env-file ocra.env ocra-cloud
```

Without Docker: `npm ci && npm run build:web && npm run build:node`, then `node dist/server.mjs` with the variables below and `MASTER_KEY` and `SESSION_SECRET` set (`openssl rand -base64 32` each). Migrations are applied at start. A trial may keep its data in a SQLite file (`DATABASE_URL=file:ocra-cloud.db`, the default); a deployment uses Postgres, since there is no moving from one to the other.

### Retention

The server deletes old records once a day (`src/db/retention.ts`). Where this document says a record is kept 90 days, it is kept `RETENTION_DAYS`: reviews and their findings, live runs, gateway calls, the audit log, merged and closed pull requests and their review flow, the inbox's read marks and index of open pull requests, the questions asked on pull request pages (Ask ocra), review threads, the heads pull requests were pushed to, finished jobs and commands, pre-merge check results, held release drafts and the daily counts. The shorter windows stay as they are, since 30 days is the least `RETENTION_DAYS` may be: an automation's runs, ended merge intents, deliveries and their claims, and a team's members (30 days), a platform's webhook deliveries (7 days), the notification centre (30 days), closed pull requests in the inbox's index (8 days). Sessions, login codes and API tokens go when they expire, whatever it says. Lowering it deletes the older records at the next daily run; raising it keeps only what was not yet deleted. The web app's data policy page states the hosted service's 90 days.

Serve it over HTTPS: session cookies are `__Host-` cookies, which browsers keep only on secure origins.

## Who may sign in

Unset, `SIGN_IN_ALLOW` lets in anyone the sign-in providers vouch for: any GitHub user, and any subject of the OpenID Connect provider. Set, it is a comma list of entries, and a sign-in that matches none is refused (`403 forbidden_for_session` with `"reason": "sign_in_not_allowed"`) before any account is made:

| Entry | Matches |
|---|---|
| `org:<organization>` | a GitHub user who is an active member of the organization. Read with the user's own token, or, when the server keeps none for them or GitHub refuses it (revoked) or does not let it read the organization, with the App's installation on the organization (`GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`); either way the App must be installed on the organization with the Members: Read permission |
| `user:<login>` | that GitHub login. GitHub lets a login be renamed and the old one taken by someone else, so prefer `org:` |
| `domain:<domain>` | a verified email address at exactly that domain (a subdomain is not the domain): on GitHub one of the user's verified addresses, which needs the App's account permission Email addresses: Read; through OpenID Connect the `email` claim when `email_verified` is true |
| `group:<group>` | through OpenID Connect, a value of the userinfo's `groups` claim, compared exactly (a self-hosted GitLab names its groups by path, such as `company/eng`; Keycloak, Okta and Azure AD need a mapper or claim that puts `groups` in userinfo) |

For example `SIGN_IN_ALLOW=org:acme,domain:acme.com`. Logins, organizations and domains are compared lowercased, a domain in its ASCII form (`bücher.example` is `xn--bcher-kva.example`); a group cannot hold a comma. The server refuses to start with an entry it cannot read, or more than 50. With a list set, GitHub's sign-in page offers no sign-up.

Sessions and API tokens are checked too. An account's answer is kept in its row with a hash of the list it was checked against: a request within the hour uses it, a later one asks again (on GitHub, live: the login, the domains, then each organization until one matches), and a changed list asks again at once. An account that no longer matches is refused on its next request with `401 unauthenticated` and the same reason, its web and CLI sessions and its API tokens alike, so leaving the organization ends access within the hour. When GitHub cannot answer (it is unreachable, or the user's token is gone and no App can read the organization), a match found within the last day stands, and after that the account is refused until it signs in again; GitHub is then asked again at most every five minutes, not on every request. A revoked token is checked as if the server kept none: the stored login for `user:`, the App for `org:`. An OpenID Connect provider is not asked again without the person: a change of their groups or email there counts from their next sign-in, while a change of `SIGN_IN_ALLOW` refuses every session at once and each person signs in again. To shut out one SSO user at once, disable them in the provider and change the list (adding a `group:` entry nobody has is enough).

## A GitHub App of your own

On GitHub, one App of the company's own does three things: people sign in with it, the console acts as each person through it (comments, reviews, merges, fixes, issues), and its installation is the bot that reviews. Create it under the organization: Settings, Developer settings, GitHub Apps, New GitHub App.

- **Callback URL** `<PUBLIC_URL>/api/auth/github/callback`, with "Expire user authorization tokens" on.
- **Setup URL** `<PUBLIC_URL>/repositories`, with "Redirect on update" on, so whoever installs the App or changes its repositories comes back to the console. The tab they left reads their repositories again when they return to it.
- **Webhook** active, URL `<PUBLIC_URL>/api/webhooks/github`, and a secret of your choosing: `GITHUB_WEBHOOK_SECRET`. The server refuses webhooks without it, and a delivery whose signature does not match answers 401.
- **Repository permissions**, each needed by what follows it:

| Permission | Access | Used for |
|---|---|---|
| Contents | Read and write | reading the code to review; committing a finding's fix, applied suggestions, learnings and configuration as the person; generated tests and docstrings as the bot |
| Pull requests | Read and write | the inbox and pull request page; comments, reviews, thread replies, labels, draft state and merges as the person; the bot's reviews and answers |
| Issues | Read and write | opening an issue from a finding |
| Checks | Read and write | the `ocra / pre-merge` check run; merge when ready reading check runs |
| Commit statuses | Read | merge when ready reading statuses; the pull request page's CI panel |
| Actions | Read and write | the CI panel's failed step and job log (read), and its re-run of failed jobs as the person (write); without it the panel still lists the checks and shows what each reported |
| Administration | Read | the merge readiness checklist's branch rule; without it those rows read unknown |
| Metadata | Read | required by GitHub |

- **Organization permission** Members: Read, for team code owners in the readiness checklist, reviews asked of a team (see Notifications) and `org:` entries of `SIGN_IN_ALLOW`.
- **Account permission** Email addresses: Read, only for `domain:` entries of `SIGN_IN_ALLOW`.
- **Events**: Push, Pull request, Pull request review, Pull request review comment, Pull request review thread, Issue comment, Check suite, Check run and Status.
- Then set `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` (the App's client), `GITHUB_APP_SLUG`, `GITHUB_APP_ID` (its number), and `GITHUB_APP_PRIVATE_KEY`: a private key generated on the App's page, on one line with `\n` for its line breaks (`awk '{printf "%s\\n", $0}' key.pem`). The server refuses to start with only one of the id and the key, or a key it cannot read.
- Install the App on the repositories it should review. Each review then gets an installation token limited to its repository.

Adding a permission later makes GitHub ask each installation, and each person on their next sign-in, to accept it.

### GitHub Enterprise Server

On GitHub Enterprise Server, create the same App on the server (Settings, Developer settings, GitHub Apps, as above) and set `GITHUB_URL` to the server's address. Everything the server calls on GitHub then goes there: sign-in (`/login/oauth/*`), the REST API (`/api/v3`), GraphQL (`/api/graphql`), the App's installation tokens for the bot, the links the console shows (repositories, issues, the App's installation page, the person's profile) and each review's clone. The review's CLI is given `GITHUB_API_URL=<GITHUB_URL>/api/v3`. Webhooks are verified with `GITHUB_WEBHOOK_SECRET` as on github.com, and the repositories they name are looked up on `GITHUB_URL`'s host. One server has one GitHub: github.com or one GitHub Enterprise Server.

A server signed by the company's own certificate authority needs it in `NODE_EXTRA_CA_CERTS` (for the server and the CLI) and `GIT_SSL_CAINFO` (for git), as for a self-managed GitLab (gitlab.md). The console shows no GitHub avatars there: where a server serves them depends on its subdomain isolation, and the console's content policy allows only github.com's.

Tested against a stand-in server (`test-node/github-enterprise.test.ts`: sign-in, the repositories the App reaches, and a hosted review posted as the bot). Not yet tried on a real GitHub Enterprise Server: how an older release answers the GraphQL fields the console reads (the merge queue, viewed files, auto-merge), and whether its webhook deliveries differ in a way the stand-in does not show.

## Company models

`MODEL_ENDPOINTS` declares the company's own model endpoints, such as an internal gateway in front of vLLM or a hosted model, as a JSON list:

```json
[
  {
    "id": "corp",
    "label": "Corp LLM",
    "base": "https://llm.corp.example/openai",
    "models": "/v1/models",
    "key": "the server's key for it"
  }
]
```

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | lowercase letters, digits and `-`, not a built-in provider's id; models are named `ocra-<id>/<model>`, such as `ocra-corp/qwen3-coder` |
| `label` | yes | the name the console shows |
| `base` | yes | an http or https URL without credentials, query or fragment; the paths are appended to it |
| `paths` | no | the paths the gateway forwards, `["/v1/chat/completions"]` when unset; the CLI needs one ending in `/chat/completions` |
| `auth` | no | `bearer` (the default) or `x-api-key`: how the key goes on the request |
| `models` | no | a GET that lists the models in OpenAI's shape; it also checks a key |
| `key` | no | the server's own key: every account's calls use it and nobody stores one. Without it, each person adds their own key for the endpoint on the keys page |
| `prices` | no | what its models cost, by model id, in US dollars per million tokens: `{"qwen3-coder": {"input": 0.4, "output": 1.2, "cachedInput": 0.1}}` (`cachedInput` is optional). The CLI counts a review's cost and its spend limit (`maxCostUsd`) with them, and the usage ledger prices each call to the endpoint at them, cache writes as input (`docs/usage-reconciliation.md`). A model without a price is counted at $0 by the CLI, and each review says so in a warning; the ledger shows its calls as unpriced |

An endpoint with a `key` is the company's bill: every account calls it through `/api/gateway`, held back only by the per-account daily caps. Without `SIGN_IN_ALLOW`, anyone who can sign in gets an account, and so does anyone with a GitHub account when people sign in with GitHub, so set it whenever an endpoint has a `key`; the server warns at start (`open_sign_in_with_server_key`) when one does and no list is set.

A gateway that speaks Anthropic's Messages protocol instead is declared with its path and key header, and reviews then run on the Direct runtime:

```json
{ "id": "corp-claude", "label": "Corp Claude gateway", "base": "https://llm.corp.example/anthropic", "paths": ["/v1/messages"], "auth": "x-api-key", "key": "..." }
```

What a company gateway usually needs:

- **Model names** are passed as the gateway spells them, with `/`, `:`, `@` and capitals (`ocra-corp/Corp/Qwen3-Coder:32k@v2`).
- **A private certificate authority** goes in `NODE_EXTRA_CA_CERTS`, and a **proxy** in `HTTPS_PROXY` with `NO_PROXY` for the hosts that are reached directly (Variables). The server's calls to the endpoint and each review's CLI both use them.
- **Rate limits:** a `429` from the endpoint reaches the CLI as it is, which waits for its `Retry-After` and sends the request again; a quota that outlasts the review ends it with the files it did not reach named.
- **The daily cap** (`GATEWAY_DAILY_CALLS`, 500 calls per account when unset) is sized for a public service. Raise it for a team that reviews every merge request, or let an account lower its own on the Budget page.
- **Prices** are yours to declare (`prices`); the server knows none for a company's models.
- **Function calling:** the models must call tools. For an endpoint that refuses them, see the engine's manual (Providers, An endpoint without function calling).

With `DEFAULT_MODELS` naming them, a colleague who signs in for the first time reviews with the company's models without setting anything. The endpoints appear in the console's "Your company" group, and the CLI reaches them through the gateway like any other provider, with the same metering and daily caps. A declaration the server cannot read stops it from starting, naming the field. Keep the filled-in environment file secret when it holds a `key`.

## Postgres

For a team, keep the data in Postgres (13 or later): `DATABASE_URL=postgres://…`. Compose runs Postgres 17 in a container beside the server, its data in the `postgres-data` volume, and a one-off `migrate` run that applies `migrations-pg/` before the server starts. To use the company's own Postgres, set `DATABASE_URL` (with its password, or `PGPASSWORD`) in `ocra.env`, and run only the `migrate`, `ocra` and `caddy` services. The tables and values are those of the SQLite schema: times are milliseconds in `bigint` columns, JSON is text. Back up with `pg_dump`.

## Several processes

`docker-compose.replicas.yml` runs several ocra processes on this machine against its database, behind the same Caddy: add it to `COMPOSE_FILE` in `.env` (`docker-compose.yml:docker-compose.replicas.yml`) and run `docker compose up -d --build`. Saving on the setup page starts again only the process that answered: run `docker compose restart ocra` after it.

A one-off `migrate` run (`MIGRATE=only`) applies the migrations first; the replicas (`OCRA_REPLICAS` in `.env`, 2 by default) start after it with `MIGRATE=off` and `RATE_LIMITS=database`. Caddy sends requests to each in turn and skips one that fails its health check. The SQLite file runs in WAL mode, so readers do not wait for the writer. For processes on several machines, point `DATABASE_URL` at Postgres or a libSQL server, with the same two settings. The inbox's live updates reach every process only on Postgres (see the inbox's stream, `GET /api/platforms/pulls/changed/stream`, below).

## Incoming webhooks

Each platform delivery whose signature (GitHub) or project secret (GitLab) checks, and that has a step to run after its answer (below), is recorded in `inbound_events` before anything acts on it, unique per platform, host and the platform's delivery id (`X-GitHub-Delivery`; GitLab's `Idempotency-Key`, else `X-Gitlab-Event-UUID`), so a redelivery answers `202` with `"duplicate": true` and does nothing. If the answer itself fails, the record goes and the platform's redelivery is taken. A delivery with no such step is not recorded, so it costs no database write: on GitHub, every delivery of a repository no account enrolled, and of an enrolled one every event but a pull request, its review or a comment (a push, a check run or suite, a status) unless an armed merge-when-ready intent waits on its commit, which a check that only started or a pending status never moves, or it is a check suite that failed on a pull request's head (its author's `checks_failed`); on GitLab, a pipeline hook unless such an intent waits on its commit or it is a merge request pipeline that failed. Telling that apart reads the delivery's fields and, only where they could move an intent, the repository's enrollment and its intents, never writing. Those run as they always did, and a redelivery of one is answered again; what its answer does (a graph build, a re-run of the pre-merge check) is keyed so that doing it twice changes nothing. What runs after the answer (the account's notices, merge-when-ready intents and a reviewed pull request's directories) runs from the record, which keeps only the fields those steps read (never a diff, description or the rest of the body) until they are done. A step that throws is tried again a minute, five minutes and half an hour later, four attempts in all, the steps that succeeded not again; a process that stops mid-way leaves the record to the next sweep once its ten-minute lease is over. A Node server told to stop (`SIGTERM`, `docker stop`) first lets the steps under way finish, within its ten seconds, then closes the database. The Node server sweeps every minute, the Worker in its hourly cron; each attempt is taken by compare-and-set, so several processes never run one twice, and a sweep takes repositories in turn. A platform call that is refused or not answered is not an error here: those steps end as they did before. Records are shared by the deployment, not an account's (a delivery arrives before any account is known, and may concern none), are not in an account's export, and go after 7 days.

## Daily reconciliation

Once a UTC day, each enrolled repository not paused is read from its platform to fill in what its webhooks missed (a delivery the platform gave up on, a server that was down). As the deployment's bot where it has one for the repository, else the enrolling account's platform link, it lists the pull requests closed or merged since the later of three days ago and the repository's enrollment, and the open ones, up to two pages of 100 each. A pull request that closed after the repository was enrolled and has no close on record gets one, with the platform's time; a close a webhook recorded is never changed. A pull request the server holds open (no close, or a close before a reopen) that the platform no longer lists open gets its close, read on its own when it is not in the closed list (up to ten per repository). An open one changed since enrollment with no flow gets one, and one whose draft state changed has it merged in, as a webhook event of the platform's last change. Then the ten open ones changed most lately, since the later of three days ago and enrollment, get their reviews read, one call each (on GitHub the first 100 reviews, on GitLab the approvals), and their asks of a review compared with the reviewers and teams the open listing names: a review someone other than the author or a bot submitted after enrollment is kept once, as its webhook keeps it (the pull request's first review and approval move earlier, the asks it answers end); an ask the platform shows and the server has none of, or holds ended before the platform's last change, starts at the run's time, never earlier, so no reminder counts a wait the server never saw; an ask the server holds waiting from before the platform's last change that the platform no longer shows ends at that change (on GitLab a reviewer who approved no longer waits, and an approval rule's group is left to its webhooks). An ask and its end are written by compare-and-set on what was read, so a webhook that arrived meanwhile stands, and a round of review it ends never tells of an ask from before it. Every write merges in the statement, as the webhooks' do (a close only when none is on record, or a later one; a flow's first times the earliest), so the two never undo each other. It runs from the hourly run (the Worker's `47 * * * *` cron, the Node server's hourly timer): each run claims at most ten repositories, at most two of one account, taking accounts in turn and the repositories read longest ago first, within its budget of calls (below). Before each listing page and single read it checks that a call is left, and a new repository is started only while at least six are; a repository can take at most 28 (a token from the deployment's GitHub App takes up to four: the App, its installation, the token, then the link's refresh if the App refused). The Node server's budget is 200 calls a run, not an environment variable. One the budget cut short keeps what it filled, gives its claim back (its `reconciled_at` returns to what it was) and is read again, from the start, by a later run, which takes it among the first, since it is among those read longest ago. The claim is a compare-and-set on `review_repos.reconciled_at`, so a repository is read once a day however many processes run. One whose platform failed or refused gives its claim back too, so a later run of the same day tries it again, after every repository not yet read that day, at most three tries a day (the retries are counted in the milliseconds before midnight its `reconciled_at` is set back to); before a GitHub repository's is given back, one more call reads its path by the platform's id, and a path that changed (a rename or transfer its webhooks missed) moves it to the new name, which the retry reads. A GitLab project's path is read by its id before its listings, one call within the six; one that has no bot and no link, or whose platform the deployment no longer serves, waits for the next day, since neither comes back within the hour. On Node, at ten per hour a deployment reads 240 repositories a day; on the Worker a small repository read by the App's bot takes up to six calls, and one more for each open pull request changed lately, so a quiet hour reads about seven, a busy one one. A deployment with more reads each less often than daily. Nothing is written to the platform, and no log line names a repository.

## The hourly run's calls

The Workers Free plan fails an invocation that makes more than 50 external subrequests (D1 queries count apart, up to 1,000), so each run of the Worker's crons makes at most 45 calls in all, counted as they go out: every call the server makes to a platform, a chat, a webhook or the GitHub App goes through one counting fetch (`src/calls.ts`), and one past the run's budget is refused without being made. The jobs take turns fairly (`src/cron-calls.ts`). First each runs within its share, all at once:

| Job | Share |
|---|---|
| Deliveries due again | 6 |
| Platform webhooks' side effects due again | 6 |
| Automation rules' writes due again, then stale rules | 4 |
| Notices held in quiet hours | 3 |
| Review reminders | 3 |
| Pull requests at risk of a review target | 3 |
| Daily digests | 3 |
| Weekly reports, then the scheduled reports accounts define | 3 |
| Armed merge-when-ready intents | 4 |
| Waiting stack merges | 4 |
| Daily reconciliation | 6 |

Then each job that wanted more runs again, one after another in that order, on what the others left. The work that can wait is last, so it yields first: an armed merge-when-ready intent's and a stack merge's webhooks move them and the sweeps only pick up what they missed, and a repository not reconciled this hour is in a later one. A job checks its budget before it claims the next piece of work, so what it does not reach stays as it was, unclaimed, for the next run. Work its budget cuts short gives its claim back by compare-and-set, so nothing is lost or sent twice: a delivery's attempt that was refused is due again at once and not counted as an attempt (a digest, report, reminder or held notice so cut goes with the next run's deliveries); a platform webhook's side effects go back with the steps left, due at once; an automation rule's retry goes back uncounted and due at once, keeping the writes the platform answered; a merge-when-ready intent goes back armed as it was (what it waited on, when it was last read), so the next run reads it first, and is never ended or said to wait on an answer that was not read; a stack merge waits as when the platform did not answer, keeping the pull requests it already moved; a repository's reconciliation is given back as above. A request is never counted, and the Node server's timers have no budget but the reconciliation's.

## Health and metrics

The setup page's Health step (`GET /api/setup/health`, behind the setup code) tests every part as the server runs now, in plain words, with what to change under each failure: the database and its migrations, the sign-in provider's discovery document, GitLab or GitHub and the review bot's token, each company model endpoint's model list with its key and the tiers' models in it, whether reviews run here and their runners report in, the public address and email.

`GET /api/health` answers `{"ok":true}` without reading anything: Docker's health check, Caddy and deploys call it, so it stays cheap. It says the process answers, nothing more.

`GET /api/health?deep=1` reads the database, on Postgres, SQLite and D1 alike, and answers 200 with `"ok": true`, or 503 with `"ok": false` and `reasons`:

| Reason | Meaning |
|---|---|
| `database_error`, `database_timeout` | the database refused a `SELECT 1`, or did not answer it within 5 seconds |
| `migrations_missing` | a migration this build expects is not applied; `migrations.missing` names up to ten, oldest first. A replica started with `MIGRATE=off` before the `migrate` run finished, or a `migrate` run that failed |
| `migrations_unrecorded`, `migrations_error`, `migrations_timeout` | the database keeps no record of applied migrations (Drizzle's `__drizzle_migrations`, or D1's `d1_migrations`), or it could not be read |
| `runner_stale` | with `RUNNER_TOKEN` set: remote runners have reported in this week, but none in the last 5 minutes (a runner asks every few seconds; its row is written once a minute). Before the first runner reports in, there is nothing to check (`runnerSeenAt: null`) |

The body also carries `migrations` (`expected`, `applied`, `missing`, and `unknown`: applied migrations this build does not know, from a newer build, which do not fail the check). Each address may ask for a deep check 20 times a minute (`429 slow_down` past it), so point a readiness probe at it every 10 seconds or more, and keep the liveness probe on the plain one.

With `METRICS_TOKEN` set, `GET /metrics` (beside `/api`, not under it) answers Prometheus' text format to a request that sends `Authorization: Bearer <METRICS_TOKEN>`, compared in constant time; any other answers 401. It counts across the whole deployment, never per account: the counts are labelled by queue, kind or state alone, and the process series by collector, engine version and schema, so no account, repository, login or secret appears, and each scrape is a few aggregate queries.

| Metric | Labels | Meaning |
|---|---|---|
| `ocra_jobs` | `queue`, `state` (`queued`, `running`) | jobs waiting or held by a worker or runner; `queue` is `review`, `reply` (answers to `@ocra` comments), `generate` (generated tests or docstrings), `learn` (declined findings read for learnings) or `graph` (code graph builds) |
| `ocra_jobs_failed_last_hour` | `queue` | jobs that failed for good in the last hour (a job retried after an error is queued again, not failed; one given up as `lease_lapsed` or `never_started` counts here too) |
| `ocra_jobs_oldest_queued_seconds` | `queue` | how long the oldest queued job has waited since it was queued; 0 with none |
| `ocra_deliveries` | `kind` (`notify`), `state` (`pending`, `delivered`, `failed`) | outgoing notification deliveries of every channel kind (Slack, WeCom, email, webhook) kept: still to be delivered, delivered, or given up on (a channel keeps its newest; retention drops them after 30 days) |
| `ocra_delivery_retries_due` | `kind` | pending deliveries whose next attempt is due: the server tries them every minute, so a number that stays up means retries are not running |
| `ocra_inbound_events` | `state` (`pending`, `done`, `failed`) | platform webhook deliveries recorded for the steps after their answer (Incoming webhooks): still to run or due a retry, done, or given up on after four attempts (records go after 7 days) |
| `ocra_merge_intents` | `state` (`armed`, `merging`) | merge-when-ready intents not yet ended |
| `ocra_process_uptime_seconds` | | seconds since this process started |
| `ocra_build_info` | `engine`, `schema` | always 1: the engine (CLI) version the server runs reviews with, and the newest migration this build expects |
| `ocra_metrics_collector_up` | `collector` (`jobs`, `deliveries`, `merge_intents`) | 1 when the collector read the database on this scrape, 0 when it failed (the failure is logged, the other collectors still answer) |

Each process answers for the database it shares with the others, so with several processes, scrape one, or keep `ocra_process_uptime_seconds` and `ocra_build_info` from each and the rest from any. The Worker serves no `/metrics`: its reads would spend D1's daily rows.

A scrape and alert rules to start from (tune the thresholds to the deployment):

```yaml
scrape_configs:
  - job_name: ocra
    scheme: https
    metrics_path: /metrics
    authorization: { type: Bearer, credentials_file: /etc/prometheus/ocra-metrics-token }
    static_configs: [{ targets: ["ocra.example.com"] }]

groups:
  - name: ocra
    rules:
      - alert: OcraReviewQueueStuck
        expr: ocra_jobs_oldest_queued_seconds{queue="review"} > 900
        for: 5m
        annotations: { summary: "A review has waited over 15 minutes: no worker or runner is taking jobs" }
      - alert: OcraJobsFailing
        expr: sum by (queue) (ocra_jobs_failed_last_hour) > 5
        for: 10m
        annotations: { summary: "{{ $labels.queue }} jobs are failing" }
      - alert: OcraDeliveryRetriesBehind
        expr: ocra_delivery_retries_due{kind="notify"} > 0
        for: 10m
        annotations: { summary: "Notification retries are due but not being sent" }
      - alert: OcraDeliveriesFailing
        expr: delta(ocra_deliveries{kind="notify",state="failed"}[1h]) > 3
        annotations: { summary: "Notification deliveries are being given up on" }
      - alert: OcraMergeStuck
        expr: ocra_merge_intents{state="merging"} > 0
        for: 15m
        annotations: { summary: "A merge when ready has been merging for 15 minutes" }
      - alert: OcraMetricsCollectorDown
        expr: ocra_metrics_collector_up == 0
        for: 5m
      - alert: OcraDown
        expr: up{job="ocra"} == 0
        for: 2m
      - alert: OcraRestarting
        expr: resets(ocra_process_uptime_seconds[30m]) > 2
        annotations: { summary: "The server keeps restarting" }
```

### Instance status

`GET /api/admin/instance` answers the deployment's state, read only, to the operators `INSTANCE_ADMINS` names, from a web session; anyone else, and everyone while it is unset, gets `404 not_found`, as for a route that does not exist. An entry names the identity an account signs in with, which never changes: `github:<id>` is the GitHub user's numeric id (`gh api users/<login> --jq .id`, or `<GITHUB_URL>/api/v3/users/<login>` on GitHub Enterprise Server), and `oidc:<subject>` the provider's `sub` claim. A login is not accepted: GitHub lets one be renamed and taken by someone else, and a provider's username is whatever it sends. At most 50 entries; the server refuses to start with one it cannot read.

The answer holds counts and health only, never an account's, repository's or login's name, id or content (`InstanceStatus` in `src/shared/instance-admin.ts`): `engine` (the `cli` and `contract` versions this build pins), `schema` (`newest`, the newest migration this build expects, and `expected`, `applied`, `missing` and `unknown` counts of the database's, null when it records none), `accounts`, `enrolledRepos`, `jobs` by queue (`review`, `reply`, `generate`, `learn`, `restack`, `fix`, `mend`, `graph`: `queued`, `running`, `failedLast24h`, `oldestQueuedSeconds`), `runners` (`lastSeenAt`, when a remote runner last asked for work this week, and `stale` past 5 minutes) and `deliveries` (`notify`: outgoing notifications `pending`, `due` and `failed`; `inbound`: platform webhooks whose steps are `pending` or `failed`), with `checkedAt`. Each read counts rows across the whole database, so poll `/metrics` instead.

## Code graphs

An account adds a repository on the console's Code graphs page (or `/api/graphs/repos`); the server then keeps a graph of its default branch (symbol names, kinds and line numbers per file, never code), built after each push from the platform's tree and blob APIs with the account's own token, reading only the files that changed. Pushes arrive at `<PUBLIC_URL>/api/webhooks/github` (the GitHub App's webhook, signed with its secret) or `/api/graphs/webhooks/gitlab` (a project hook with the secret the server answers when the project is added). Builds older than 14 days are deleted daily, except each repository's newest; an account rebuilds a repository's graph from its branch's head, purges its graphs or removes it at any time, from the same page. The page is in the console only where `CODE_GRAPH` is not `off`. Builds run in the server process with the engine's tree-sitter parser (`@open-cr-agent/code-graph`); with several processes on one database, each build is claimed by one of them. `PUBLIC_URL` must be set for GitLab, whose token refresh names the server's address. A graph is stored gzipped, in pieces of the `graph_chunks` table (migration `0079` moved it there and does not carry older graphs over: each is built again at its repository's next push or Rebuild). A review the server runs for an enrolled repository is given the account's graph of it (`ocra review --graph`), and its first review adds the repository to the account's Code graphs. On Cloudflare Workers the remote runners build the graphs instead ([runner.md](runner.md), Code graphs).

The pull request inbox (`GET /api/platforms/pulls`) reads, live as the user, the pull requests asking their review, theirs open, those open and assigned to them (GitHub's `assignee:@me` search in the same request as the others; GitLab's `assignee_id` across every project) and theirs merged in the last week, each with its `roles` (`reviewer`, `author`, and `assignee` only on a pull request that is neither of the others, so one the user opened or was asked to review and is also assigned stays where those put it), with their labels and the verdict of the account's newest ocra review of each (`blocking` when it is `significant_concerns`). A pull request asking the user's review through a team they are on, on an enrolled repository, carries `requestedTeam` (`org/slug`; none when the review was also asked of them), from the team asks the webhooks recorded (see Notifications); GitHub's listing already holds such pull requests, so there this names why; GitLab lists only merge requests naming the user a reviewer, so those an approval rule asks of a group the user is on (as the kept copy of its members says) are read one by one, the 10 newest asks at most per load (`more` when there were more), and listed while still open. An account names up to 20 sections of it (`/api/pull-views`: list, add, `PUT /<id>` to rename, change, move or hide, `PUT /order` with every id, `DELETE /<id>`), each filtering by role (asked to review, mine or assigned), repository, author (me, others or logins), review state, draft, checks, verdict, label and days since the last update; names are unique per account. An account without sections is offered four defaults, which `POST /api/pull-views/defaults` keeps so they can be changed. `?group=views` also answers each visible section with the pulls it holds, evaluated on the server over the same listing. Open pulls stacked in one repository (one's base branch is another's head, neither from a fork) carry `stack: {id, position, size}`, position 1 the bottom, worked out from the listed pulls alone: an unlisted pull in the middle splits the stack, and the size counts listed pulls only.

The listing also answers `changedAt`: when a webhook last said a pull request of one of the account's enrolled repositories changed (the pull request itself, a review, a review thread or comment on it, a finished check suite or merge request pipeline of it; a check of a branch without one does not count), or when the account's newest review arrived, read before the listing; null before any. `GET /api/platforms/pulls/changed` answers the same value from the database alone, with no platform call, and the open console reads the listing again only when it moved past the listing's own. While its tab is in view, the console holds `GET /api/platforms/pulls/changed/stream` open (Server-Sent Events, a web session only): whatever moves the change time pushes a `pulls` event to the account's open streams (a JSON array of `{ repoId, number, kind }`, no titles or bodies): a webhook about a pull request of an enrolled repository, and a stored review upload (`kind` `review`; `repoId` and `number` null unless the review was of a pull request of a repository the account enrolled). The console then asks `/pulls/changed` once. A stream sends a comment line every 25 seconds and ends after 5 minutes; the browser reconnects, and the console asks once on each `ready` for what came between. An account holds at most 6 streams (on Node, 6 per process); past that, or when a stream fails, the console asks every 30 seconds instead. On Workers each account's streams meet in a Durable Object (`PULL_EVENTS`). On Node with Postgres each process sends its events with `NOTIFY` on the channel `ocra_pulls_changed` (the account id and the events, nothing else) and holds one connection of its own that `LISTEN`s there, so a console hears every process's changes; a connection pooler in front of Postgres must pass `LISTEN` through (PgBouncer only in session mode). While that connection is down the process tells its own streams only, logs `pull_events_local_only` once, and connects again with backoff up to a minute; once back it ends its streams, whose consoles reconnect and catch up. On Node with SQLite or a libSQL server the events stay in the process's memory, so where several processes serve one address a console hears only the changes its own process received, and the rest within 5 minutes. A pull request of a repository the account has not enrolled moves nothing: the console then shows it as of its last read, as before.

The server keeps an index of the pull requests of the account's enrolled repositories (`pull_index`), so the inbox can often be answered without a platform call. Each pull request webhook (GitHub's `pull_request`, GitLab's merge request hook) is merged into its row as the platform has it, unless the row already holds a newer platform update time, so a late or repeated delivery never takes it back. The daily reconciliation fills it from the listings it already reads, with no call of its own, closes the rows it no longer lists open, and marks the repository read in full; a repository not read in full in the last two days, or paused, counts as not indexed. Each live inbox listing also keeps what it read of the user's pull requests in enrolled repositories, checks and review state included, which webhooks do not carry. When a live listing held no pull request of the user outside the indexed repositories and matched, pull request for pull request and role for role, what the index then answers, the next loads of the inbox on that platform for 5 minutes are answered from the index, with no platform call and the same fields; a delivery the index cannot follow (a new head, a finished check, a commit status or check run on an indexed head, a review, a comment, a merge queue change, any event of a repository not indexed) sends the next load to the platform again. A pull request in a repository the account has not enrolled can so appear up to 5 minutes late on a new load. Closed rows are deleted 8 days after they last changed, open ones 90 days after; unenrolling a repository deletes its rows, and the export holds them (`pullIndex`).

Each listed pull request is `unread` when it changed since the account last saw it, with the first `unreadReason` that holds (`new`, `marked`, `commits`, `merged`, `ocra_review`, `replies`, `activity`), from the listing's `updatedAt` and head, the account's newest ocra review and the review threads kept from webhooks (below); no other platform call is made. Each also has `repliesWaiting`: how many review threads the user started on it have a reply by someone else newer than both the `updatedAt` of the user's read mark (or the inbox baseline without one; every reply counts while it is marked unread) and the user's own last reply in the thread; `replies` is the reason when nothing before it holds and one waits. The server keeps one read mark per pull request (platform, repository, number, the platform's `updatedAt` and head the user saw, and when), which never moves to an older `updatedAt`. The pull request page marks its pull request read with `POST /api/pulls/seen` (`platform`, `repo`, `number`, `updatedAt` and `head` from `GET /api/pulls/files`), and `POST /api/pulls/seen/bulk` marks up to 250 read (`read: true`, each with its `updatedAt` and `head`) or unread (`read: false`). A pull request with no mark is read when its `updatedAt` is at or before the account's inbox baseline, and otherwise unread (`new` when it was opened after it): the baseline is when the account first listed its inbox, kept from then on, and never earlier than 90 days ago, so a new account starts with nothing unread and a mark that expires leaves its pull request read. Marks go 90 days after they were last set, and the account's export holds them and the baseline (`inboxSince`).

A pull request's page reads its diff live as the signed-in user (`GET /api/pulls/files`, at most 4 MB of diff per page) and sends their comment, review and merge to the platform as them (`POST /api/pulls/comment`, `/review`, `/merge`); only a web session may, and nothing read or sent is kept. A review or merge names the head commit the user read, and one that moved since answers `head_moved` instead of acting. GitLab takes approve and comment as verdicts, and merge or squash as merges. A review shared with its findings also keeps its walkthrough (overview, files in groups, diagram), redacted again on the server, on the review's page and in its export. A finding has a fix when the CLI shared one (0.10.0 and later) and the server's own redaction left its replacement whole. That fix is committed to the pull request's branch with `POST /api/pulls/apply-fix`, as the user, only while the pull request is still at the commit that was reviewed and the file is unchanged since; the finding is then marked fixed. "Write the PR description" drafts the pull request's description without a model (`GET /api/pulls/description-draft?platform=…&repo=…&number=…`) from ocra's stored review of its head now, else its newest review, and says which head that is: the verdict and the walkthrough's overview, the walkthrough's change list, the linked tasks, and risk notes by severity, the open findings' titles while the account shares findings and the counts otherwise; the review's text is written as plain one-line text (no HTML, Markdown's inline syntax escaped). ocra's part sits between `<!-- ocra:description:start -->` and `<!-- ocra:description:end -->`, so a later draft replaces only that part and keeps the rest of the description. The user edits it and saves it as themselves with `POST /api/pulls/details` (its `body`, below), only while the description still reads as the draft's page read it, so another person's edit since is never overwritten. Cycle time (`GET /api/insights/cycle?platform=…&days=…`, optionally `&repo=…` for every author's pull requests in one repository) reads up to 50 pull requests merged in the last 90 days at most, as the user, and times each from opened to the first review or comment by someone else and to merged; nothing is kept.

"Open issue" on a finding of a review of a pull request drafts an issue without a model (`GET /api/findings/:id/issue-draft`): the title is the severity and the finding's title as one line, and the body names the severity, the category and the verification, links the pull request and the finding's lines in the file at the reviewed head (only https addresses, and only for a path inside the repository), and quotes the finding's text and suggestion as plain text (no HTML, Markdown's inline syntax escaped, a zero-width space after every `@` so nobody is mentioned). The user edits it and opens it in the reviewed repository as themselves (`POST /api/findings/:id/issue` with `title`, one line of at most 255 characters, and `body`, at most 65,536; GitHub's issues API, GitLab's project issues with scope `api`). One issue is opened per finding: the server claims it in `finding_issues` (unique per account, review and finding) before calling the platform, so a second click answers the issue already opened (`created: false`), a click while another is opening it answers `pending`, and a refused or unreached call gives the claim up; a claim left by a request that died is taken over after a minute. The review's page lists each finding's `issue` (`number` and `url`, or null). The record goes with its finding and is in the account's export.

The page's CI panel reads the head's CI live as the user, and keeps nothing of it. `GET /api/pulls/ci?platform=&repo=&number=` (`PullCiView`) lists the head's GitHub check runs (each name's latest, up to 300) and commit statuses, or the jobs of GitLab's newest pipeline on the head (up to 300), each with its state, times, duration, address, and for a failed GitHub Actions job its first failed step (the first five read) or for GitLab its failure reason, and, on a repository the account enrolled, what the fix loop's last round did with a failed check of that name (`mend`, as `GET /api/auto-review/mends` gives it in `checks`) when that round read this head. A job failed when it failed or timed out, not when it was cancelled or skipped; a GitLab job allowed to fail is `neutral`. `GET /api/pulls/ci/log?…&job=<id>` (`PullCiLogView`) answers the end of a job's log: GitHub Actions' job log (its redirect followed once, to an https address, without the user's token), GitLab's job trace, else what a check run of another app reported (`check_output`) and its address. At most the last 256 KiB of a log are read, and of a log over 32 MiB nothing. It is first narrowed to the part that holds the failure, so the steps that ran after it do not fill the tail: on GitHub Actions from the last `##[group]Run …` line before the last `##[error]` line through that line, on GitLab the lines of the last `step_script` section; a log with neither is kept whole. It is then cut as the engine's fixer cuts it (the last 200 non-empty lines, without timestamps, terminal sequences and control characters, then the last 20,000 characters), then redacted with the contract's pass, answered with `cache-control: no-store`, and never logged or kept. `POST /api/pulls/ci/rerun` with `platform`, `repo`, `number`, `head` and optionally `job` (`PullCiRerunAnswer`) runs again as the user, only while the pull request is still at that head (`stale` otherwise): on GitHub the failed jobs of each failed workflow run of the head (`rerun-failed-jobs`, at most 10 runs), or the one Actions job; on GitLab each failed job of the pipeline (job retry, at most 10), or the one job, of that head. Another app's check run cannot be run again from here (`not_rerunnable`), and a platform's refusal answers `refused`; each re-run is in the audit log as `pull.checks_rerun`. On GitHub the log and the re-run need the App's Actions permission (above).

"Explain this failure" (`POST /api/pulls/ci/explain` with `platform`, `repo`, `number`, `job` and optionally `model`, a web session; `PullCiExplainView`) asks the account's own model, with its own provider key, why one job failed and what to look at. Its prompt holds the end of the job's log as the CI panel reads it (or what the check reported), the job's name and the first 100 changed paths, each fenced as data. The model is asked for at most 150 words and no patch; the answer is cut at 4,000 characters and redacted. ocra runs nothing of the repository, and nothing is committed or kept: neither the log nor the answer is stored or logged. A job with neither a log nor a report answers `explanation: null` with no model call. The call counts against the gateway's daily cap (`daily_limit` past it) and is recorded as a gateway call, as Ask ocra's are.

A pull request's tour and highlights (`GET /api/pulls/tour` and `GET /api/pulls/highlights` with `platform`, `repo`, `number` and `head`, a web session; `PullTourView` and `PullHighlightsView`) are not built yet: both answer `not_found` with `available: false`, make no model call and store nothing. A host that plugs a generator into `Host.pullGuides` answers what it makes for the pull request at that head.

Each file on the page has a viewed tick, and the page counts how many of its files are viewed. `GET /api/pulls/files` gives each file's `viewed`, and `POST /api/pulls/viewed` with `platform`, `repo`, `number`, `head` and 1 to 100 `paths` ticks them (`viewed: true`) or unticks them, only while the pull request is at that head (`head_moved` otherwise). On GitHub the tick is GitHub's own, read and set as the user through GraphQL (`viewerViewedState`, `markFileAsViewed`, `unmarkFileAsViewed`), so it matches GitHub, which clears it when the file changes; the first 1,000 files say, and nothing is kept. GitLab has no API for it, so the server keeps each tick in `pull_file_views` with a SHA-256 of the file's diff at the time (GitLab names no blob per file); a tick counts only while the file's diff at the current head hashes the same, so a file that changed in a later head reads as not viewed, as does a file whose diff GitLab did not send at any new head. Ticks are kept for 90 days and exported with the account.

"Changes since last review" shows only what changed from a head the user reviewed or saw to the current head (`GET /api/pulls/since?platform=…&repo=…&number=…`, optionally `&since=<sha>`, any case). It offers two heads to compare from: the head of the user's latest submitted review (on GitHub, GraphQL's `viewerLatestReview`, a pending one left out; on GitLab, the head of the user's newest diff comment among the merge request's last 100 notes, or the version the merge request was at when they last commented or approved) and the head of the user's read mark. Without `since` it compares from the review's head, else the read mark's. It answers the files changed in PullFilesView's shape, read as the user through GitHub's compare API (at most 300 files) or GitLab's repository compare, at most 8 MB of answer and 4 MB of diff, with `state`: `changes`, `same` (already the current head), `rebased` (a force push left that head out of the current history, from GitHub's comparison status or GitLab's merge base), `unavailable` (the platform could not compare it) or `none` (no head to compare from). A diff along the history includes what a merge of the base branch brought in. Nothing read is kept.

Every push to a pull request is a version, numbered from 1 (`GET /api/pulls/versions?platform=…&repo=…&number=…`). The heads come from two places, merged by head: the webhooks of an enrolled repository, which keep each head a pull request is pushed to (GitHub's `pull_request` `opened`, `reopened` and `synchronize`; a GitLab merge request hook that opens, reopens, or updates with `oldrev`) in `pull_versions`, one row per head with the platform's update time as its push time, unique per enrolled repository, pull request and head, so a head pushed again keeps its first push; and, read live as the user, what the platform still lists: GitLab's merge request diff versions (the newest 100), or on GitHub the heads either side of the timeline's last 100 force pushes (`HEAD_REF_FORCE_PUSHED_EVENT`) and the current head. Each version says when it was pushed (null when only its commit's time is known) and `kind`: `first`, `fast_forward`, `rewrite` (a force push or rebase), or null when neither says; on GitHub a head that is no force push's is a fast forward when the timeline's force pushes were all read, and GitLab does not say. `complete` is true when the list starts at the opening (GitLab listed fewer than 100 versions, or a webhook kept the opening push). `GET /api/pulls/versions/compare?platform=…&repo=…&number=…&from=<sha>&to=<sha>` compares any two heads as the user: along the history, as "Changes since last review" does, when `from` is an ancestor of `to` (`compare: history`), else tree to tree (`compare: trees`): GitLab's repository compare with `straight=true`, or GitHub's git commits and recursive trees APIs (at most 8 MB each), which name the files that differ by blob, with no lines (`lines: false`). Heads are kept 90 days and exported with the account; nothing the platform answered is kept.

How far a pull request moved since ocra's latest review of it (`GET /api/pulls/review-changes?platform=…&repo=…&number=…`): the review is the newest the account uploaded for that pull request, and the answer gives its head, `state` from that head to the current one (as `GET /api/pulls/since` says it), `commits` (GitHub's comparison `total_commits`, the length of GitLab's comparison commits; null after a rebase), `versions` (pushes after the reviewed head, from the versions above; null when the head is in none), `openFindings` (the review's findings still open at its head) and `automatic` (whether the enrolled repository reviews every push; null when the account did not enroll it). `reviewChanges` is true on an enrolled repository reviewed only when asked, when the pull request moved past a review that left findings open: the page's "Review changes" sends `POST /api/pulls/review-now` for the current head, and a hosted review of a pull request reviews only what changed since the previous review (the engine's own incremental review, which carries earlier findings over and marks those it sees fixed), or everything again after a rebase. Nothing reviews until someone asks. Nothing read is kept.

A line or range comment in a review may carry a suggestion (at most 16,384 characters and 200 lines, on new lines only, a range at most 101 lines): the server writes it as GitHub's ` ```suggestion ` block on the comment's lines, or as GitLab's ` ```suggestion:-N+0 ` on the range's last line (a GitLab range comment is anchored on its last line). `GET /api/pulls/threads?platform=&repo=&number=` reads the pull request's review threads live as the user, at most 100 with 50 comments each, with their resolved state and suggestions: on GitHub parsed by its rules (one block per comment, on a thread that is not outdated, on new lines) and checked against the lines the comment was written on; on GitLab as GitLab itself parsed them, applicable when it says so and the note is on the latest diff. An outdated suggestion is listed and never applied. `POST /api/pulls/apply-suggestions` applies up to 20 of them as one commit by the user, only while the pull request is at the head the page read (`head_moved` otherwise), and answers `not_applicable` when a suggestion's lines changed since its comment. On GitHub it goes through the same contents API commit as a finding's fix, so the suggestions applied together must be on one file, and the token needs Contents and Pull requests write; on GitLab it uses GitLab's suggestion apply API (one, or a batch in one commit) with the user's `api` scope, and the user needs Developer on the source branch, as on GitLab itself. `POST /api/pulls/apply-batch` commits up to 20 items, ocra's findings' fixes and review suggestions together, as one commit by the user, only while the pull request is at the head the page read: a finding's fix only when its review was of that head, a suggestion only when it is applicable there. Two items that change the same lines in the same way are applied once, for both; when they change any of the same lines differently, the one earlier in the request is applied and the later answers `conflict`, whichever platform. Each item answers applied, or skipped with `not_found`, `no_fix`, `stale`, `conflict`, `not_applicable` or `not_sent`, and the rest is committed. One file changed goes through the same contents API commit as a single fix; several on GitHub through its git database (a tree on the head's tree, keeping each file's mode, a commit whose parent is the head, and the branch moved only as a fast forward, so a branch that moved answers `head_moved`), on GitLab through its commits API with an action per file, each guarded by the file's last commit. A GitLab suggestion applied this way is part of the user's commit, so GitLab does not mark it applied; its lines changed, so it is no longer applicable. `POST /api/pulls/resolve-thread` resolves or reopens a thread as the user: GitHub's `resolveReviewThread` and `unresolveReviewThread` mutations for a thread of that pull request (GitHub lets the pull request's author and anyone with write access resolve), GitLab's discussion resolve. Nothing read or sent is kept.

`POST /api/pulls/reply-thread` (`thread`, `body` of at most 65,536 characters) replies to a review thread as the user: GitHub's `addPullRequestReviewThreadReply` mutation, only for a thread the pull request's listing reads (`refused` otherwise), and a note on GitLab's discussion of that merge request. `GET /api/pulls/draft` reads whether the pull request is a draft and whether it is open, and `POST /api/pulls/draft` (`draft`) makes an open one a draft or ready for review: GitHub's `convertPullRequestToDraft` and `markPullRequestReadyForReview` mutations, and on GitLab the title's `Draft:` prefix, which GitLab reads as the draft state (its prefixes `Draft:`, `[Draft]` and `(Draft)` are taken off for ready); one that is not open is refused unsent, one already so is answered done unsent, and a change is kept as `pull.marked_draft` or `pull.marked_ready` in the audit log. `GET /api/pulls/labels` reads the pull request's labels and one page of 100 of the repository's to pick from (`truncated` on a full page), and `POST /api/pulls/labels` adds and removes up to 20 each by name (no comma, none in both): on GitHub through the issues API, adding first and then removing only the labels the pull request has, on GitLab in one update, and is kept as `pull.labels_changed` (the label names asked to be added and removed) in the audit log. GitHub needs no permission beyond Pull requests write, GitLab the `api` scope; the platform decides who may, as on its own page. Nothing else read or sent is kept.

`POST /api/pulls/details` edits a pull request's title (`title`: `from`, the title the page showed, and `to`, one line of at most 255 characters, not blank), its description (`body`: `from` and `to`, at most 65,536 characters each), or both, as the user: GitHub's `PATCH /repos/{owner}/{repo}/pulls/{number}` and GitLab's merge request update. Neither platform guards an edit, so the pull request is read just before: a field that no longer reads its `from` (line endings aside) is refused as `stale` (409) and nothing is sent, and a field that already reads its `to` is not sent. `POST /api/pulls/state` (`state`: `closed` or `open`) closes or reopens it: GitHub's `state`, GitLab's `state_event` `close` or `reopen`; a merged pull request (or a locked GitLab merge request) is refused unsent, one already so is answered done unsent. Both answer a pull request the platform does not show the user as `not_found` (404), a platform 409 as `stale`, its other refusals (403, 422, such as reopening one whose branch is gone) as `refused`, and a used-up allowance as `upstream_unreachable`. They are kept as `pull.details_edited` (the fields' names, never their text), `pull.closed` and `pull.reopened` in the audit log. GitHub needs Pull requests write, GitLab the `api` scope; the platform decides who may, as on its own page.

`POST /api/pulls/update-branch` (`head`, the head the user saw) brings a pull request's branch up to date with its base as the user: GitHub's `PUT /repos/{owner}/{repo}/pulls/{number}/update-branch` with `expected_head_sha`, which merges the base into the branch, and GitLab's merge request rebase. A head that moved is refused as `stale` (409), unsent when the server reads it so first; GitLab's rebase takes no head, so the merge request is read just before. It answers `updating` when the platform took it (it works asynchronously, the new head follows), `up_to_date`, `conflicts` (GitHub's 422; on GitLab a merge request with conflicts is not sent, since its rebase would fail out of sight), `forbidden` when the user may not push to the branch, `not_open`, and a used-up platform allowance as `upstream_unreachable` with reason `platform_rate_limited`. It is limited per minute like every platform call and kept as `pull.branch_updated` in the audit log. GitHub needs Contents and Pull requests write, GitLab the `api` scope and push access to the source branch. The readiness checklist's `canUpdateBranch` says when to offer it: GitHub's merge state `BEHIND` (the branch rule requires it up to date) or GitLab's `need_rebase`, and never while the branch conflicts.

The page also suggests up to five reviewers (`GET /api/pulls/reviewers?platform=&repo=&number=`), read as the user and kept nowhere: the owners the repository's CODEOWNERS at the pull request's base gives its changed files (at most 300; GitHub's `.github/`, root and `docs/` locations, GitLab's root, `docs/` and `.gitlab/`, at most 128 KB; the last matching rule wins, per section on GitLab, and teams, groups, roles and emails are listed as owners but not expanded), and, for a repository the account enrolled, who reviewed its pull requests in the last 90 days, ranked higher for reviews of pull requests that changed the same directories (`reviewed_these_paths`). Those directories are each changed file's top-level and second-level directory, at most 32 per pull request, kept in `pull_paths` for 90 days and exported with the account: after a review or GitLab approval arrives by webhook, the server reads the pull request's changed files (at most 300) once per head, as the bot where it has one and else as the account that enrolled the repository. Each suggestion says why, how many changed files it owns, the changed directory it reviewed the most pull requests in (for example 4 in `src/db`), its recent reviews and how many open pull requests ask it for a review now as the user sees them, which lowers its rank; the author and bots are left out. `POST /api/pulls/reviewers` with `platform`, `repo`, `number` and up to 10 `logins` asks them for a review as the user.

A repository's learnings (`.ocra/learnings/*.md`, ADR-0037 of the engine) are read live at its default branch as the signed-in user (`GET /api/learnings?platform=…&repo=…`, 50 files a page, `&after=<id>` for the next), parsed as a review would read them; files a review would skip are listed with the reason. `GET /api/learnings/proposals` lists the open pull requests from the repository's own `ocra/learnings-*` branches (at most 10) with the learnings each adds, changes or deletes. An addition, edit or deletion (`POST /api/learnings`, `POST /api/learnings/delete`) is committed as the user on a new `ocra/learnings-*` branch and opened as a pull request, or committed on the default branch with `direct: true` when the platform lets the user; it names the file's blob as the console read it, and a file changed, added or deleted since answers `conflict` instead of being overwritten. Only a web session may, and nothing read is kept. Each learning listed comes with how many of the repository's uploaded reviews were given it in the last 90 days, and when the newest was (`usage`), from the learning ids a review uploads with a pull or merge request, or with its findings.

A repository's committed review configuration, `.ocra/config.json` and its rules in plain language in `.ocra/rules.md` or as JSON in `.ocra/rules.json`, is read and changed the same way. `GET /api/repo-config?platform=…&repo=…&file=config|rulesMarkdown|rules` (`config` when left out) answers the file's text at the default branch, its parsed value or why it is not JSON (the Markdown rules are not parsed: `value` is `null`), its blob (`null` when there is no file), what the engine would refuse in it (`errors`, at most 20, and `refusal`, the same issues worded as the CLI prints them when it refuses the file, or `null`), and the `$id` of the JSON Schema an editor can check it with (`schema`; the rules files have none). `POST /api/repo-config` with `{ platform, repo, file, text, expected, direct? }` commits the text as the user on a new `ocra/config-*` branch opened as a pull or merge request, or on the default branch with `direct: true` when the platform lets the user; `expected` is the blob the edit was made on (`null` for a file that must not exist yet), and a file changed since answers `conflict`. Text that is not JSON, is over 64 KiB, or does not fit the engine's schema is refused, as are Markdown rules longer than the contract's `MAX_RULES_MARKDOWN_CHARS` (20,000 characters, as the engine counts them), with `invalid_body` and its `issues` (paths under `text`) before anything is sent. The schemas are the engine's: the configuration's is the pinned `@open-cr-agent/cloud-contract`'s `configSchema`, with the checks the CLI makes when it loads the file (endpoint addresses, credential variable names, unique merge check ids), and the rules' is the JSON Schema of the pinned `@open-cr-agent/core`'s rule schema (`src/engine-schemas.ts`, made by `node scripts/engine-schemas.ts`; a test fails when it drifts). A refusal of a POST carries the same `refusal` text. The console adds nothing the file could not already say: what a review runs from it is the engine's decision, as for a file committed by hand.

A pull request's impact (`/api/graphs/repos/<id>/impact?pull=<number>`) is computed from that graph on request: the platform's pull request API gives the changed files' diffs, the symbols their changed lines (not the unchanged lines shown around them) touch on the graph's side are the changed ones, and their uses are the other files' identifiers of the same name, matched by name and not type-resolved. The code line of up to 40 uses is read from the platform at the graph's commit for the answer and not kept. The review page of a pull request's review shows it in a rail beside the findings when the console keeps a graph of that repository; a review uploaded before this server stored pull requests (migration `0028`) has none. On Workers the runner computes it when it reviews the pull request and the server keeps that answer (`pull_impacts`, 90 days, in the account's export) instead of computing it on request.

The account's audit log (`GET /api/audit`, web session only) lists its own events newest first, at most 50 a page (`limit`), the next page from `after=<next>`; `kind` keeps one kind, and `since` and `until` (milliseconds since the epoch, `until` exclusive) a time range. It records sign-ins and sign-outs, a session ended from the list, a terminal approved or denied, an API token made, revoked or first used, a GitLab account connected, a change to the settings, sharing or budget, a provider key saved, checked or deleted, a channel, automation rule or enrolled repository (and its review depth) added, changed or removed, a live review's link or people changed, and a review, merge or fix sent from the console, besides merge when ready. Each event keeps a few named fields (`AUDIT_FIELDS` in `src/shared/audit.ts`, the only ones answered), never a key, token, webhook address or body. Events go after 90 days and are in the account's export.

## API tokens

A script or CI job reads the account's data with a personal API token instead of a session. Tokens are made, listed and revoked from a web session only (`POST /api/tokens` with `{ "name", "scopes", "expiresInDays" }`, `GET /api/tokens`, `DELETE /api/tokens/<id>`); making one needs a sign-in within the last 15 minutes, like replacing a provider key or deleting the account. A token must expire, within 365 days, and an account holds at most 20. The secret (`ocra_pat_` and 43 characters, 256 random bits) is answered once, when it is made; the server keeps only its SHA-256, the name, the scopes, its first 15 characters (to tell it apart in the list), when it was made, when it expires and when it was last used (written at most once a minute). An expired token is refused, then deleted by retention; a revoked one is deleted at once. The export lists tokens without their hashes.

Send it as `Authorization: Bearer ocra_pat_…`. A token reaches only `GET` routes listed in `API_TOKEN_ROUTES` (`src/shared/api-tokens.ts`), each with one scope, and answers `403 forbidden_for_session` (with the `scope` a listed route needs) everywhere else:

| Scope | Routes |
|---|---|
| `reviews:read` | `GET /api/reviews`, `GET /api/reviews/<id>` |
| `insights:read` | `GET /api/insights/cycle`, `/flow`, `/impact`, `/reviewers`, `GET /api/findings/insights` |
| `pulls:read` | `GET /api/platforms/pulls`, `GET /api/pulls/files`, `/threads`, `/readiness` |

No scope writes anything, nor reaches tokens, keys, channels, sessions, settings or the account. The `pulls:read` and cycle-time routes read the platform live as the account's linked user, as the console does, so a `pulls:read` token reads private source: the diffs, review threads and pull requests of every repository that user can see, private ones included. Each token has its own allowance of `ACCOUNT_CALLS` per minute, and all the account's tokens together one more, apart from the account's own calls (`429 slow_down` past either). Signing out, ending sessions or a new sign-in does not revoke a token: revoke it from a web session (`DELETE /api/tokens/<id>`), or delete the account. The audit log records a token's creation (its first characters, scopes and expiry), its revocation and its first use, never the secret.

"Draft release notes" lists the pull requests merged between two refs of a repository and drafts notes from their titles, without a model: `GET /api/release-notes?platform=…&repo=…&from=…&to=…` (a tag, branch or commit each; a name git would refuse is answered `not_found`), read live as the signed-in user and kept nowhere. On GitHub it is one compare call (at most 250 commits) and one GraphQL query for those commits' pull requests, of which only those merged as a commit of the range count (their merge, squash or last rebased commit); on GitLab one compare call and at most three pages of 100 merged merge requests updated since the range's oldest commit, matched by their merge, squash or head commit. At most 200 are listed, and `truncated` says when the range held more. Each title's Conventional Commit type picks its section: `feat` Added, `fix` Fixed, `perf` Performance, `refactor`, `chore`, `ci`, `build`, `test` and `style` Maintenance (left out of the body unless `hidden=true`), anything else Other changes, and a `!` or a `BREAKING CHANGE:` footer in the description Breaking changes. Each line links its pull request and credits its author with a zero-width space after the `@`, and titles are escaped as in a finding's issue, so the notes mention no one. With `reviews=true` each line also names the account's newest review of that pull request (its verdict and finding count; `review` in `pulls`). `POST /api/release-notes/publish` with `{ platform, repo, tag, target, name, body, draft: true }` saves the user's edit as a draft release as them: on GitHub it edits the draft release of that tag when one is among the newest 100 releases, refuses `tag_exists` when the tag or a published release of it exists, `target_missing` when `target` is no branch or commit, and otherwise creates a draft release, which makes the tag at `target` only once it is published. The token needs Contents read and write, which the App already has for committing; nothing is checked or claimed on this server, so two saves at once of a new tag can make two drafts. GitLab keeps no draft releases: a release makes its tag at once, and one with a future `released_at` (an "upcoming release") is still a published release with its tag. So on GitLab the server holds the draft for the account until it is published: the publish checks, as the user, that `target` is a commit, branch or tag of the project (`target_missing` otherwise) and that no tag of that name exists (`tag_exists`), then keeps the draft and answers `{ "outcome": "held", "draft": { id, tag, target, name, body, version, updatedAt } }`. One draft is held per account, project and tag (a unique key), at most 100 per account. A save names the `version` it edits; a save of a tag already held without it, or from an older version, answers 409 `stale` with the current `version`, so two tabs never overwrite each other. `GET /api/release-notes` on GitLab lists the project's held drafts as `held` (the newest 50 edits). `POST /api/release-notes/held/<id>/publish` with `{ "version": n }` checks the tag and target again and creates the release (`POST /projects/:id/releases` with `tag_name`, `ref`, `name`, `description`), which makes the tag at `target`; it answers `{ "outcome": "published", "url": … }` and drops the held draft, or `tag_exists`, `target_missing` or `refused` (the user may not make releases there, which needs the Developer role or a protected tag's rights) and keeps it. `DELETE /api/release-notes/held/<id>?version=n` discards one. A held draft is kept 90 days after its last save, and the account's export holds them as `releaseDrafts`.

## Rotating the master key

The image carries the re-wrap tool beside the server: `node dist/rewrap-master-key.mjs` reads the server's own `DATABASE_URL`, the old key from `MASTER_KEY_PREVIOUS` and the new one from `MASTER_KEY`, and re-wraps every sealed row as on Workers (`docs/rotation.md`):

1. Make the new key (`openssl rand -base64 32`). In `ocra.env`, set `MASTER_KEY_PREVIOUS` to the current key (the one Compose made: `docker compose exec ocra cat /secrets/master_key`) and `MASTER_KEY` to the new one, which wins over the secrets volume's, then `docker compose up -d`. New rows are sealed with the new key; old rows still open with the previous one. The setup page's saved settings are sealed again under the new key as the server starts.
2. Check, with no change: `docker compose exec ocra node dist/rewrap-master-key.mjs`. It reports each table: rows to re-wrap, rows already under the new key, rows that failed.
3. Re-wrap: the same command with `--apply`. It writes nothing when a row opens with neither key, writes in batches, each update only while the row still holds the wrapped key it read, then reads every table back and fails unless each row opens with the new key. Run it again until it does; a second run re-wraps only what is left.
4. Remove `MASTER_KEY_PREVIOUS` from `ocra.env` and `docker compose up -d`. Keep the old key until a review through the gateway has worked, then destroy it. `MASTER_KEY` stays in `ocra.env`, which `backup.sh` does not copy: keep a copy of it with the backups.

Without Docker, run `node dist/rewrap-master-key.mjs` after `npm run build:node`, with the same variables. Neither key, nor anything a row seals, is printed. Back up the database first.

## Limits of this first version

- One GitHub per server: github.com or one GitHub Enterprise Server (`GITHUB_URL`), not both.
- Until GitHub or OpenID Connect is set, nobody can sign in and the server opens on its setup page. An account belongs to the identity it signed in with: the same person through GitHub and through SSO is two accounts.
- Back up the database and the secrets with `selfhost/backup.sh` (Backups); there is no Time Travel as on D1.
- The setup page holds one model gateway. Several, or prices per model, are `MODEL_ENDPOINTS` (Company models), which then locks the page's Models step.

## Auto review

Enable auto review with a bot and `PUBLIC_URL`. A Node deployment runs jobs locally by default; it can also use [remote runners](runner.md) with `RUNNER_TOKEN`. A Worker requires remote runners. When a deployment can queue jobs but no runner is online to take one, the job waits in the queue.

One account enrolls each repository (`/api/auto-review/repos`); its models, keys, budget and rules apply. The repository's **Automatic** switch starts off unless enrollment sets `automatic: true`. Turn it on in Auto review (`PUT /api/auto-review/repos/:id/automatic` with `automatic`) to queue a review when a pull request opens, reopens, leaves draft or gains commits. GitHub events arrive at `/api/webhooks/github`; GitLab uses a project hook with its own secret at `/api/auto-review/webhooks/gitlab`. See [the GitLab setup guide](gitlab.md#4-start-and-enroll) for the events to enable and when the server can install the hook. A newer head supersedes a queued one, and one pull request is reviewed once at a time.

The enrolling account can also use **Review now** from the pull request page, even with Automatic off. `POST /api/pulls/review-now` takes `platform`, `repo` and `number`; `GET` with those query parameters returns the latest job. The server reads the current head as the user, reuses a queued or running review of that head, and reruns an already reviewed head only when `force: true`. Set `depth` to `quick`, `standard` or `deep` to override the repository default for the job. The response reports the repository depth and the job's override (null when it uses the default). Automation rules that skip reviews do not apply to this request. The endpoint returns `not_found` when auto review is disabled on the deployment.

Many GitHub repositories are enrolled at once with `POST /api/auto-review/repos/bulk` (web session only) and `{"fullNames": ["owner/repo", ...], "automatic": false}`, at most 20 names: each is read as the user, as one enrollment is, so only repositories the user reaches through the App are enrolled, one after another, and the answer says of each, in order, `enrolled`, `already` (with the repository) or `refused` with a `reason`: `not_found` (the user does not reach it), `taken` (another account enrolls it) or `limit` (the account has 100). An account can also enroll the repositories later added to one of the App's installations: `GET /api/auto-review/installations` lists those the user reaches with their switch, and `PUT /api/auto-review/installations/<id>/auto-enroll` with `{"enabled": true, "automatic": false}` turns it on (web session only; one account per installation, the database decides, so another account's turning it on is refused with `invalid_body`; `enabled: false` turns it off). Then the App's `installation_repositories` event (GitHub sends it to every App, with no subscription) enrolls each repository it adds, up to 100, after the webhook is answered, read as that account's user and with the switch's `automatic`, skipping one any account enrolled already. A delivery that adds more than ten goes on in the hourly run, within its share of calls for webhook deliveries, from where it stopped. An installation created later has no switch until the account turns one on; its repositories are enrolled in bulk. Each change of a switch is in the audit log (`auto_review.auto_enroll_changed`, with the installation's owner), and the switches are in the account's export as `autoEnrollInstallations`. GitLab projects are enrolled in bulk with `"platform": "gitlab"` (at most 10, each with its hook), and a GitLab group's new projects by a daily sweep once its switch is on: [gitlab.md](gitlab.md), Many projects, and a group's new ones.

Repository lifecycle. An enrolled repository is known by its platform's id, so it survives a rename or a transfer: GitHub's `repository` event (`renamed`, `transferred`; the App must subscribe to Repository events), any later GitHub pull request event that names it at a new path, or else the daily reconciliation moves it to the new name: it reads a GitLab project's path by its id before its listings (`GET /projects/<id>`), and a GitHub repository's when its listings fail (`GET /repositories/<id>`; GitHub answers an old name with a redirect, which the server does not follow). A GitLab hook's path is not taken for a rename, since its secret proves only the project's id. That move rewrites, for each account that enrolled the repository or keeps its graph, every row that names it by path (the enrollment, the graph, finding threads, merge-when-ready intents, stack merges, unread marks and viewed files) and, by the account's hash of the old and new address, its reviews (and their pull request's repository), live reviews, remembered findings and repository name, all in one transaction; a row whose new key is already taken is left as it is. Each rename is in the audit log (`auto_review.renamed`, with the `previous` name). The webhooks need no platform call for this. A repository that stops being reachable is paused instead of unenrolled, so its settings and history stay: removed from the App's installation (`installation_repositories` `removed`; reason `removed`), deleted (`repository` `deleted`; `deleted`), its installation suspended (`installation` `suspend`; `suspended`) or uninstalled (`installation` `deleted`; `uninstalled`; the App's installation is per user or organization, so these name every enrolled repository of its owner). Pausing gives up its queued jobs of every kind (`failed`, error `repository_paused`); no runner claims a job of a paused repository, no review is queued from its webhooks, and the daily reconciliation skips it. It resumes when added back to the installation, when the installation is unsuspended, or installed again on it (by the repositories the new installation is given, or all of the owner's), and when the account enrolls it again, which reads it as the user; a deleted repository resumes only that way. `GET /api/auto-review/repos` answers each repository's `paused` (`removed`, `deleted`, `suspended`, `uninstalled` or null), and each pause and resume is in the audit log (`auto_review.paused`, `auto_review.resumed`, with the reason). GitLab project deletion is not detected; its jobs fail as before until the project is unenrolled.

When a person answers one of ocra's findings in its thread, or resolves the thread, on a pull request of an enrolled repository, the server reads the pull request's declined findings five minutes after the last such event (`ocra learn feedback --pr`, ADR-0069 of the engine): the engine keeps only the reasons of people with write access, drafts a learning from each with the account's models, and opens one pull request that adds them under `.ocra/learnings/`. Each enrolled repository chooses what happens to it on the Learnings page (`PUT /api/auto-review/repos/:id/learn` with `learn`): `merge` (the default) merges it once its checks pass, `propose` leaves it for a person, `off` reads nothing. One pull request is read at a time, at most 10 learnings a run, and a finding already turned into a learning is not drafted again.

On GitLab, an enrolled project can have its own access token, which its reviews post with in place of `GITLAB_BOT_TOKEN` (`PUT /api/auto-review/repos/<id>/access-token` with `{ token }`, `DELETE` to remove it; web session only). Give a group access token (one per group, for all its projects) or a project access token, with the Developer role and scope `api`: its bot user posts the reviews. The server refuses a person's token, a token without scope `api` or without the Developer role on the project, and one GitLab rejects. It is kept encrypted with the master key, bound to the project's row, never answered (the listing says `hasAccessToken` and `accessTokenBot`, the bot's username), logged or exported, and is deleted when removed or when the project is unenrolled. A job of a project whose token GitLab answers with 401 fails at once with `token_rejected`. With the GitLab application and `PUBLIC_URL` set, the Node server runs hosted reviews for such projects without any bot variable; details in [gitlab.md](gitlab.md), Without a server-wide bot.

Each review clones the repository into a new temporary directory and runs the installed `ocra` CLI there, as CI does: `ocra review --pr <n> --publish --no-repo-config` (`--mr` on GitLab), signed in to this server as the enrolling account through a session made for the run. Nothing from the pull request runs. It runs on the account's saved runtime, or on Direct when the account chose none (the CLI's own default is OpenCode). It posts as the bot, and gets only the variables it needs, none of this server's secrets: those of the certificate authorities and the proxy are passed on. The directory and the session are removed when the run ends, whatever its outcome; a failed run is retried twice, five and ten minutes later. The image includes git; a server run outside it needs git on its `PATH`.

An account's reviews wait at its daily limit of gateway calls (`GATEWAY_DAILY_CALLS`, or the account's own budget when that is smaller): none is started until the UTC day turns, and one the limit cut short, whether it finished part of the change or nothing, is queued again for the next day and shown as "Daily limit reached" on the Auto review page.

A hosted review's findings are kept on the server, with the code each one quotes (redacted like any upload), from the first review the server runs for the account, whether or not the account shares findings: the server read that code to review it. Keeping them is what shows them on the pull request's page, the review and the findings pages, and what the notices and reports count; it applies to the run's own session only, so a review from the user's machine still sends findings only while the account shares them. The account switches it off under Account & privacy (`PUT /api/account/sharing/hosted` with `{ enabled, deleteExisting }`, which can also delete what is stored when findings are not shared); once off, a later hosted review does not turn it back on. The choice is in the account's export and its audit log (`sharing.hosted_changed`).

Each enrolled repository has a review depth (`GET` and `PUT /api/auto-review/repos/<id>/depth` with `{ depth }`, set from the web session only; `depth` in the repository listing), which the hosted review passes to the engine as `--depth` (its preset fills only what no other layer sets, effort among it: low at `quick`, high at `deep`) and holds with settings of its own: `standard`, the default, sets nothing and runs the review as before; `quick` turns off the performance, docs and AGENTS.md reviewers and sets `showPreExisting: false`, so only correctness and security findings on changed lines are reported, posts at most 10 of them inline and only warnings or worse (`minInlineSeverity: "warning"`, `maxInlineComments: 10`; the engine lists the rest in the summary comment and keeps them in the report), and sets `ultra: false`; `deep` adds `--ultra` (every reviewer at every tier, two samples each, more than twice the cost with its high effort, still under the account's budget). A review asked for on a pull request's page may take another depth (above). The depth's settings go in the run's `--config` file, which the engine reads above the account's settings (those fill only what it leaves out); an account that turns `ultra` on gets it at `standard` and `deep`, not at `quick`. A review run in CI from a committed configuration is not given a depth. Answers to `@ocra` and `ocra generate` do not use it.

A hosted review still runs with `--no-repo-config`, so the CLI reads nothing from the clone; the server reads the repository's `.ocra/config.json` itself and passes part of it on in the same `--config` file (`src/auto-review/hosted-config.ts`). It reads the file with the bot's token at the head of the enrolled repository's default branch, never at the pull request's head and never from a fork, as the console's configuration editor writes it; it takes at most 64 KiB and checks it with the pinned contract's `configSchema`. Only these keys apply: `include`, `exclude`, `reviewers.<id>.enabled` and `reviewers.<id>.minTier`, `verify`, `judge`, `showPreExisting`, `maxTasks`, `maxCostUsd`, `minInlineSeverity`, `maxInlineComments`, `ultra` and `github.requestChanges`. Every other key is dropped, among them what could run code, send code elsewhere or read outside the change (`plugins`, `pluginSettings`, `runtime`, `providers`, `models`, `effort`, `extends`, `trackers`, `projectDocs`), the run's resources (`concurrency` and the timeouts, which the job's lease bounds) and `github.botLogin`, which decides whose comments are trusted. The server's settings win key by key: a reviewer the profile turns off stays off, the profile's `showPreExisting` stands, the bot stays the one named by the server, and the lower of the file's `maxCostUsd` and the account's spend cap applies. The inline comment limits and `ultra` only hold the review tighter than its depth, or where the depth sets none the account's settings: a `minInlineSeverity` at or above theirs, a `maxInlineComments` at or below theirs, and `ultra: false`, which also drops `deep`'s `--ultra`; a looser value (a lower floor, more inline comments, `ultra: true` where the review would not run it) is dropped, the rest of the file still applies, and the job is marked `repo_config_ignored`. A depth's limits are what was chosen for the review, and ultra doubles its cost, so the file in the repository cannot raise them. Account settings fill what the result leaves out, as the CLI layers them under any configuration (an `exclude` in the file, even `[]`, keeps the account's out). A file that cannot be read, is larger than 64 KiB or does not fit the schema is not used at all: the review runs as if there were none, and the job is marked `repo_config_ignored` (shown in the console under the repository's last review), not failed. Reading it costs a hosted review three calls to the platform (the repository, its default branch, the file) when the job is claimed, on the Worker for a remote runner and in the server's process otherwise; `@ocra` answers, `ocra generate` and learnings do not read it.

A comment that mentions `@ocra` on an enrolled repository's pull request, written by a person (never a bot), queues an answer, once per comment: `ocra reply --pr <n> --comment <id>` (`--inline` for a review comment, `--mr` on GitLab) runs the same way, and the CLI answers in the comment's thread or decides there is nothing to answer. GitHub sends these as the App's issue comment and pull request review comment events; on GitLab, tick Comments (note events) on the same project hook. A failed answer is retried like a review.

A comment with a line that is only `@ocra` and a command (outside a quote or code block) is a command instead, run once per comment (`pull_commands`, unique on the repository and comment id) after the webhook's answer:

| Command | What it does |
|---|---|
| `@ocra review` | queues a review of the pull request's current head, as Review now does (a head already reviewed is not reviewed again) |
| `@ocra pause` | stops reviewing the pull request as it gains commits (`paused_pulls`); a review asked for still runs |
| `@ocra resume` | reviews it as it gains commits again |
| `@ocra resolve` | resolves ocra's open review threads (those whose first comment is a finding's), at most 20 per command |
| `@ocra fix` | asks the pull request's fix loop for the open findings the judge kept of its current head, at most 20, as Fix with ocra does, where the repository's level is `commit` (elsewhere it answers where on the console to turn Fixes on); the bot labels the pull request `ocra: fixing` until no round waits or runs (`mend_jobs.labeled`), and each commit's note says how to undo it |
| `@ocra stop` | stops the fix loop: a round that waits does not run and its findings are put off (`deferred`, which may be asked for again); a round under way finishes and commits what it fixed, and none runs after it (`mend_jobs.stop`) |
| `@ocra generate tests`, `@ocra generate docstrings` | queues `ocra generate` for the head, committed to the branch |
| `@ocra help` | lists the commands |

Only a person the platform says may push to the repository is obeyed, read as the bot: GitHub's write, maintain or admin permission (the App's Metadata read permission), GitLab's Developer role or above. Anyone else's command is recorded as `refused` and not answered, so no one outside the repository makes the bot write. Each command is answered with one comment in the pull request's conversation, as the bot; it makes at most 40 platform calls. Any other `@ocra` comment, an unknown word included, is a question as above. A pause lasts until `@ocra resume`, the pull request is closed or merged (as its webhook says, or the daily reconciliation finds; a pause made after a reopen stays), or the repository is unenrolled.

The console reads a pull request's commands with `GET /api/auto-review/repos/<id>/pulls/<number>/commands`, answered as `{ paused, commands }`: the newest 20, each `{ command, outcome, createdAt, finishedAt }` (`outcome` is `pending`, `done`, `refused` or `failed`), never the comment or who wrote it. `PUT` and `DELETE /api/auto-review/repos/<id>/pulls/<number>/pause` (web session only) pause and resume it as the commands do, answered as `{ paused }`; a change is in the audit log as `auto_review.pull_paused` or `auto_review.pull_resumed`. A command still `pending` an hour after it was made had its run die after the webhook's answer: the daily retention run marks it `failed` and never runs it again, so a late retry cannot act twice.

The daily retention deletes the record of a review, an answer and a generation of tests or docs (`review_jobs`, `reply_jobs`, `generate_jobs`, `learn_jobs`: the pull request, the commit or comment, the state and the error) 90 days after it ended, done, failed or superseded; one still queued or running is never deleted. A command's record (`pull_commands`) goes 90 days after it was made. After that, the same commit or comment can be queued again.

A job whose run died (a process or runner that stopped mid-way) stays running until its lease lapses (45 minutes for a review, 10 for an answer, 20 for generated tests or docs), then is queued again when the next job is claimed, or by the daily retention run; a run that died counts as one of its three runs, so a job that has had three fails with `lease_lapsed` instead. A job still queued seven days after it was queued (no runner took it) fails with `never_started`. Each is moved by compare-and-set on its state, so a run that finishes meanwhile keeps its result, and neither calls a platform or model.

### Findings' threads on the platform

What a person does on the platform to the thread of ocra's comment of a finding is kept with the finding, for an enrolled repository, from the same webhooks: who resolved the thread or opened it again (their platform login) and when, and the newest reply a person wrote in it, as the reason the finding was declined. A comment that starts a thread and starts with ocra's marker (`<!-- ocra:finding <fingerprint> -->`) puts the thread on record, one row per platform thread (`finding_threads`, unique per repository and thread, so a redelivery changes nothing); a resolution and a reply each move forward only by the platform's clock, so one delivered late changes nothing either. A bot's reply or resolution, and those of whoever wrote the comment (ocra under a person's token), are never taken as a person's.

- **GitHub** sends a resolution as the App's Pull request review thread event (`resolved`, `unresolved`), which needs no permission beyond Pull requests, only the event ticked on the App; without it only replies are kept. The event carries the thread's comments, so it also puts on record a thread whose first comment the server never saw. A reply is the Pull request review comment event, kept for a thread on record.
- **GitLab** sends nothing when a discussion is resolved. When a person writes in a finding's discussion (the project hook's Comments), the server reads that discussion once, as the bot or else the enrolling account's link, in the delivery's work after its answer and within the run's calls, and keeps whether it is resolved, by whom and when; a discussion found open again after it was resolved is kept as `unresolved`, at the note's time and with no login, since GitLab says neither. A resolution with no note after it is not seen.

The reply's text is cut to 2,000 characters and redacted like a finding's, and kept only when the account keeps that finding (it shares findings, or the review was the server's); deleting the stored findings (Account & privacy) drops the kept replies, and the rows go after 90 days without a change, like review threads. `GET /api/reviews/<id>` answers it on each finding as `platformDismissal`: `{ state: "resolved" | "unresolved" | null, by, at, reason, reasonBy, reasonAt, redacted, truncated }` (ISO times; `null` when nobody touched the thread; a finding commented in several threads shows the one acted on last), and the account's export holds the rows (`findingThreads`). Threads resolved from the console's pull request page go through the same webhook on GitHub.

## Automation rules

An account sets up to 50 rules (`/api/automations/rules`), each a set of conditions that must all hold and the actions taken when they do. A `queued` rule runs when a pull request of an enrolled repository is queued for review, and can match the repository, the author (on GitLab known only when the merge request opens), the base branch, a title pattern (`*` and `?`) and labels. A `reviewed` rule runs when a pull request's review is uploaded, and can match the repository, a critical finding and the verdict. The other triggers run on an enrolled repository's pull request as its webhooks say: `ready_for_review` when it leaves draft (once per head), `approved` when someone other than its author or a bot approves it (once per GitHub review, once per GitLab approver), `checks_failed` when its own CI fails on its head (a GitHub check suite of an App other than ocra's, a GitLab merge request pipeline; once per head), `labeled` when a label is added (once per label and pull request, its name compared case-folded), and `merged` when it merges (once). These match the repository, the author (on GitLab read from what its earlier events stored when the hook does not name it), the base branch, the title and labels, except `checks_failed`, which matches the repository, author, title and files only. A `labeled` rule requires `labels`, which there means the label added is one of them. A `stale` rule runs, from the hourly run (the Worker's automations share, the Node server's hourly timer), on an open pull request out of draft whose last stored event (opened, pushed to, edited, labelled, reviewed; a comment is not one) is `staleHours` (1 to 720, required) ago or more; it runs once per quiet spell, keyed by when the spell began, so again only after a new event and another `staleHours`, and never on a spell that went stale more than seven days before the run, at most 200 pull requests an account a run. It matches the repository, author, title and files. A condition a trigger's event cannot answer is refused when the rule is saved (`TRIGGER_CONDITIONS` in `src/shared/automations.ts`). Any rule can match the changed files: include and exclude globs read as `.gitignore` reads them (`*`, `?` and `**`, case ignored, at most 20 of each), held when at least one changed file, or with `every` each of them, is included and not excluded. The files are read from the platform when the rule is tried, as the bot or else the account's link, at most 300 of them; a rule they cannot decide (unreadable, or more files than that) is logged as skipped with its reason, never as matched. The actions add labels, request reviewers and post a plain comment as the ocra bot, notify one of the account's channels, or skip the review (`queued` only). A `queued` rule can also assign reviewers (`{"kind": "assign_reviewers", "strategy": "suggested" | "round_robin" | "least_loaded", "count": 1–5, "logins": [...], "codeOwnersFirst": true}`, one such action a rule): `suggested` asks the best of the reviewers the console suggests for the pull request (its code owners, recent and same-directory reviewers, fewer open review requests), `round_robin` the next of `logins` in turn (the rule's place in the list is moved by compare-and-set, so two pull requests opened at once get different ones), `least_loaded` those of `logins` with the fewest open review requests; `logins` (up to 20) is required for the last two and refused for the first. The author and bots are never asked, those already asked count towards `count` (nothing is asked when the pull request has that many), and with `codeOwnersFirst` the owners of changed files in CODEOWNERS at the base come first. It reads and writes the pull request as the bot, and assigns once per rule and pull request whatever events follow (`automation_assignments`, unique per rule, repository and number, keeping the logins asked; 90 days, in the account's export as `automationAssignments`): a reopen logs `already_assigned`, a pull request with its count `enough_reviewers`, one with no one left `no_candidates`. When the pull request could not be read the claim is given up for the next event; a request the platform did not answer is tried again with the same logins. The bot writes only on repositories the account enrolled, and only on a server with a bot: elsewhere those actions are kept and logged as needing a self-hosted server. A `queued` rule acts when the pull request opens, reopens or leaves draft; on a push only its skip applies. Each rule runs once per event (the run's unique index on rule and event key), `/api/automations/dry-run` (which takes `quietHours` for a stale rule) says which rules match a described pull request, and `/api/automations/runs` lists what each run did, kept for 30 days. A bot write the platform did not answer (a timeout, a 5xx or a 429) is tried again a minute and then five minutes later, three attempts in all, by the Node server's loop, and on a Worker with a bot by its hourly run, within its budget of calls (see The hourly run's calls), so there a retry waits for the hour (a run shows its `attempts` and, while one is due, `retryAt`); a refusal is not. `/api/automations/dry-run` takes the changed files as `paths`, and names a rule on paths it was given none for as skipped.

## Pre-merge checks

An enrolled repository can carry up to 20 checks (`/api/merge-checks/repos/<id>/checks`, managed from the web session only), each `off`, `warn` or `block`: a linked issue (optionally open, or carrying a label), a title that starts with one of a list of prefixes or matches a glob of `*` and `?` (never a regular expression), a description that is filled in (a template's HTML comments do not count) and has the named section headings, a size limit in changed files or lines, no unresolved critical ocra finding on the reviewed head, and a check written in plain words. A hosted review of the pull request is given the repository's enabled plain-language checks in its configuration, each under an id made from the check and its text, and uploads whether the change passed or failed each; a check counts the outcome only under the id of its current text, so an edited check waits, saying so, for the next review, as it does when the review could not tell. A review run elsewhere is not given them. The linked issue check waits, saying so, until the review of the head uploads the linked issues it found. Linked issues' titles and labels, and the checks' reasons, are kept only while the account shares findings.

The server evaluates a pull request's checks on its current head when the webhook queues it, when its title or description is edited, and when its review is uploaded, and posts the result as the bot: one check run named `ocra / pre-merge` on GitHub, updated in place when the result changes (the App needs Checks write), or one commit status of that name on GitLab (the bot needs at least the Developer role). A blocking check that fails makes it fail; a failing warning makes it neutral on GitHub and success on GitLab, with the failure in its summary; a blocking check that waits on the review (a linked issue, critical findings, an instruction) keeps it pending (in progress on GitHub) until the head's review lands, unless the repository's pre-merge checks turn off "Wait for the review", when it counts as not evaluated and fails nothing. A head that is never reviewed stays pending, so hold only where reviews run on every push. A result is posted once per head and result. GitHub's Re-run on that check run, or on the App's check suite, evaluates the head again and updates the same check run (the App needs the check run and check suite webhook events); a re-run of another App's run, or one already being posted again, is ignored. GitLab has no re-run for a commit status: push, or edit the title or description, to evaluate again. Without a bot, as on Workers, nothing is posted, but the pull request's page still reads the result (`/api/pulls/checks?platform=&repo=&number=`), evaluated as the signed-in user. A head's result (`merge_check_runs`) is deleted by the daily retention 90 days after it was last posted, or after it was first stored when it never was; a head evaluated after that is posted as a new check run.

## Merge when ready

On a pull request's page the signed-in user can arm "merge when ready" with a merge method (`POST /api/pulls/merge-when-ready` with `platform`, `repo`, `number`, `method`, the `head` they read and optionally `keepOnPush`; `GET` with the same query answers the intent and whether this server can stand in; `DELETE` with `platform`, `repo` and `number` cancels it). Only a web session may. The platform's own auto-merge is used first, as the user: on GitHub, auto-merge (the repository's "Allow auto-merge" setting), armed at the head the user read; on GitLab, merge when the pipeline succeeds (`auto_merge`). It waits on what the platform requires and nothing else: the `ocra / pre-merge` check and a review's critical findings hold it only where branch protection (GitHub) or the project's merge checks (GitLab) require that check to pass.

Where the platform's auto-merge is off, or the pull request could merge already, the server keeps the intent itself, on a repository the same account enrolled (see Auto review) on a server that runs reviews: the Node server with a bot, or a Worker that queues them for remote runners ([runner.md](runner.md)); elsewhere the answer is `unavailable` and nothing is kept. The intent (one per pull request and account: who armed it, the method, the head, the state and why) is moved by the enrolled repository's webhooks: a pull request's push, edit, review, merge or close, and a finished check suite, check run, commit status or pipeline. It merges, as the user and through the same merge as the page's (which names the head, so a moved one is not merged), once the platform says the pull request is mergeable (required checks and approvals pass, no conflicts), the pre-merge checks are not failing or pending, and ocra's review of the head has no unresolved critical finding. One runner merges it: the database's compare-and-set moves it from armed to merging, and a claim older than five minutes is taken over. A webhook that never came (a check that finished unheard) does not leave it armed: a sweep reads again, as the webhooks would, the intents on enrolled repositories that nothing has moved for 15 minutes and the merges whose claim lapsed, those untouched longest first, at most 20 a run (the Node server's timer every minute; the Worker's hourly run, within its budget of calls, see The hourly run's calls). An intent armed on the platform whose close webhook never came ends as merged or closed once a close after its arming is on record (from a webhook, or the daily reconciliation), in the same sweep, with no platform call, in the audit log only. A push disarms it unless the user kept it armed on new commits, which moves it to the new head; one armed natively is then turned off on the platform too. Every arming, merge and stop is in the account's audit log, a channel that hears about `merge_when_ready` is told how it ended, and an intent is deleted 30 days after it ended, or 90 days after it was last moved.

The server fallback needs, beyond what auto review needs, the GitHub App's Checks and Commit statuses read permissions and its check suite, check run and status events, besides pull request and pull request review; on GitLab, the project hook's Pipeline events, besides Merge request events. The merge itself is the user's, so their token needs what the page's merge needs: Contents and Pull requests write on GitHub, scope `api` on GitLab.

A pull request's stack (`GET /api/pulls/stack?platform=&repo=&number=`, read from the open pull requests' branches, up to ten pages of 100) merges from the bottom up to one of its pull requests as a job the server runs (`POST /api/pulls/merge-stack` with `platform`, `repo`, `number`, `method` and `heads`, the stack as the page read it, bottom first, each with its head). Only a web session may start it, and one runs per pull request at a time: a merge under way holds every layer of its chain (`stack_merge_layers`, one row per layer, unique per pull request and taken in the database with the merge, given up when it ends, in the account's export as `stackMergeLayers`), so a start from any layer one holds, also after the bottom it started from merged, answers that merge as `running` and starts nothing, and of two starts at once whose chains share a layer one is taken. It merges the bottom as the user once the platform would merge it, then retargets the next layer onto the trunk, brings its branch up to date where the repository requires that (and takes the head the platform made), waits for its checks and the platform's other rules, merges it, and so on; the open pull requests stacked on a merged layer but not in the merge are moved onto the trunk too. It stops with a reason on a failed check, conflicts, a refusal (permission), a layer that gained commits or was closed, or after three days. A request (the start, a status read, a webhook) moves it at most 20 platform calls on, so a tall stack whose layers can all merge is answered in progress (`waiting`) and goes on with the next read, webhook or sweep, never past what one Worker request may call. A channel that hears about `stack_merge` is told once how it ended: that it merged, or the layer it stopped at and why (not a cancel, which the user did); the repository need not be enrolled. `GET /api/pulls/merge-stack?platform=&repo=&number=` with any layer of the merge answers the newest one holding it (`StackMergeAnswer`), also once the bottom it started from merged, and reads it again from the platform when it has waited 15 seconds; `DELETE` with `platform`, `repo` and `number` (any layer) cancels it, though a step already sent stays done. On a repository the account enrolled, the webhooks that move merge-when-ready intents move it at once; elsewhere it moves when its page reads it and in the sweep (a minute apart on Node, hourly on Workers). On an enrolled repository, a pull request merged on the platform also has the open ones whose base was its branch moved onto its base, as the enrolling account.

Restacking after a merge. A squash or rebase merge leaves the pull requests stacked on the merged one carrying its original commits. An enrolled repository can let the ocra bot rebase and force-push them, whoever wrote them: `PUT /api/auto-review/repos/<id>/restack` with `{"restack": true}` (a web session; off by default, each change in the audit log as `auto_review.restack_changed`). With it on, each open pull request the merge moved onto the merged one's base (by the merge's webhook or by a stack merge, not the layers a stack merge merges itself, nor one a stack merge holds) is queued once per merge (`restack_jobs`, unique per repository, pull request and merge commit; deleted 90 days after it ended, in the account's export as `restackJobs`) for a runner (docs/runner.md): it clones the repository as the bot, runs `git rebase --onto <base> <merged head>` on the pull request's head and pushes with `--force-with-lease` on the head it had when queued. No code of the repository runs: no hook, no filter, merge or diff driver (the system's and the runner user's git configuration are not read). It ends `restacked` (the push is in the audit log as `stack.force_pushed`, and the pull requests stacked on that one are queued next, onto its new head), `conflict` (nothing pushed; the bot comments on the pull request to run `ocra stack restack` locally), `lease_lost` (someone pushed meanwhile; left as it is) or `skipped` with a reason (`switched_off`, `stack_merge`, `up_to_date` after a merge commit, `push_refused` when the platform refused the bot's push, such as a protected branch). With it off, the pull requests are only moved, as before. `GET /api/auto-review/repos/<id>/restacks` answers the switch and the 50 newest restacks (`RestackHistoryView`). The GitHub App needs Contents write (as for generated tests); on GitLab the bot must be allowed to force-push the branch. A pull request GitHub moved by itself, because it deleted the merged branch before the merge's webhook was handled, is queued from its own `pull_request.edited` delivery instead: where its old base is the head branch of a pull request merged in the last two hours, its new base is that one's base, and the platform confirms the merge, it is queued under the same key (the merge commit GitHub names), so the merge's own webhook and the move's never queue it twice. The merged one is the one the index (`pull_index`) holds; when the move's delivery is handled before the merge's has indexed it, the platform is asked instead, in one call listing the 20 pull requests most lately updated from the old base (`pulls?state=all&head=<owner>:<branch>`; on GitLab `merge_requests?state=all&source_branch=<branch>`), and the latest of them merged into the new base within the two hours is taken, unless one of them is still open (the branch lives on). A move's restack so reads the platform at most twice (the listing and the merge's standing); these calls are not a stack merge's and do not count toward its budget of 20 a request. That call is made only where the repository has restacks on, so on such a repository any change of a pull request's base is a delivery the server keeps and handles. GitLab does the same for at most four merge requests when it deletes the merged source branch (the merge request's "delete source branch" option): each move's update hook names the old target in `changes.target_branch`, and it is queued the same way, under the merge's squash or merge commit, else its head. A user's own move off a branch merged lately, and the move ocra makes itself after a merge, send the same hook and pass the same checks; the key keeps them from queuing twice.

Fix with ocra. A finding of a hosted review of an enrolled repository that came without a fix can have one asked of `ocra fix` (engine 0.19, ADR-0077): `POST /api/auto-review/fixes` with `{"finding": "<id>"}` (a web session) answers `queued`, `requested` (a request for that finding and head exists: `job` is it), `has_fix` or `not_open` (`FixRequestView`); `GET /api/auto-review/fixes/finding/<id>` answers its request (`FindingFixView`) and `GET /api/auto-review/fixes?platform=&repo=&number=` a pull request's (`PullFixJobsView`). Each finding is asked once per reviewed head (`fix_jobs`, unique per account, finding and head; one that failed may be asked again; deleted 90 days after it ended, in the account's export as `fixJobs`), at most 50 an account a UTC day (`daily_limit` past it), each in the audit log as `pull.fix_requested`. A runner clones the repository with a read-only bot token and runs `ocra fix --pr|--mr … --head <the reviewed head> --finding <file> --json --config <file>` signed in as the account (its key, models and spend limit; its gateway calls count against its daily limit, which a fix waits out like any hosted job). The answer is checked against the request (the finding's fingerprint and head) and recorded (`outcome`: `proposed`, `rejected`, `not_fixable`, `stale`, `head_moved`, with `reason`); a proposed fix is written into the finding, unless it got one meanwhile, where the pull request page commits it as it does a review's (`POST /api/pulls/apply-fix`, `apply-batch`). The answer is in the audit log as `pull.fix_answered` and in the notification centre as `fix_finished`; a run that gave up is a `job_failed` notice. Findings keep `lowConfidence` and their `evidence` (redacted) from the upload, which `ocra fix` reads; one uploaded before reads as not low confidence, without evidence.

A finding's rule. From engine 0.24 (ADR-0080) an uploaded finding may name the rule or learning it applies (`rule: {kind: "rule" | "learning", id}`, the contract's `FINDING_RULE_KINDS` and `FINDING_RULE_ID`; a malformed one reads as none). It is stored on the finding (`rule_kind`, `rule_id`), answered as `rule` (null when none was named, which is not to say no rule applied) on a review's findings, in `GET /api/findings` (filtered with `&rule=<kind>:<id>` or `&rule=none`) and in the export, and grouped in `GET /api/findings/insights` as `byRule`: the 20 groups with the most findings, keyed `<kind>:<id>` and labelled with the id, and `otherRules`, the rest summed. A learning's id is its file name; a rule without an id in its configuration is named from a hash of its text by the engine, so its row starts again when the text changes. Findings uploaded before name none.

The fix loop. An enrolled repository has a level for the fixes people ask of ocra, `propose` until the account sets it to `commit` (`PUT /api/auto-review/repos/<id>/mend` with `{"mend": "commit"}`, a web session; `auto_review.mend_changed` in the audit log). At `commit`, `POST /api/auto-review/mends` with `{"findings": ["<id>", …]}` (at most 20 open findings of one review of a pull request) asks the pull request's fix loop for them (engine 0.20, ADR-0078) and answers `queued`, `requested` (each already waits or was answered) or `not_enabled` (`MendRequestView`); `GET /api/auto-review/mends?platform=&repo=&number=` answers the loop and its findings (`PullMendView`). There is one loop per pull request (`mend_jobs`, unique per repository and number) and one item per finding (`mend_items`), each counted against the same 50 requests an account a UTC day as Fix with ocra, and in the audit log as `pull.mend_requested`. Fifteen seconds after the last request a runner clones the repository as the bot that may commit and runs one round, `ocra mend --pr|--mr … --level commit --findings <file> [--state <file>] --json --config <file>`, signed in as the account, on the findings that wait, the most severe first. Each edit passes the engine's gate and its verifier call; the edits that pass are one commit by the bot on the head the round read, never a force-push, and nothing of the repository runs: the pull request's own checks test the commit. What the round printed is recorded: the loop's outcome (`committed`, `nothing`, `stopped`, `head_moved`, `not_writable`), its commit and the state the next round reads; each finding's outcome (`fixed` with the commit, `rejected`, `deferred`, `needs_human`, `gone`) and reason. A finding fixed is marked fixed; one put off beside a commit, or asked for during the round, waits for the next round, which is queued at once; one rejected or put off without a commit may be asked again. A commit is in the audit log as `pull.mend_committed` and in the notification centre as `fix_finished`; a round that gave up is a `job_failed` notice. With the level back at `propose` a queued round runs nothing. A loop is deleted 90 days after its last round ended, its items with it, and both are in the account's export (`mendJobs`, `mendItems`).

`GET /api/pulls/readiness?platform=&repo=&number=` answers what still stands between a pull request and its merge as one checklist (`PullReadinessView`), read live as the signed-in user and kept nowhere: draft, conflicts, approvals, CODEOWNERS coverage (each owner group of the changed files, approved or not at a head that still counts), required checks, unresolved threads and ocra's pre-merge checks, each `met`, `unmet`, `pending` or `unknown`. On GitHub it is one GraphQL query (at most 100 changed files, threads, checks and reviews); the branch rule (required approvals, code owner review, stale review dismissal, required check names) needs the App's Administration read, and without it those parts are `unknown` unless the platform's own review decision or a check's `isRequired` answers them. The rulesets on the base branch are one more REST call (`GET /repos/{owner}/{repo}/rules/branches/{branch}`, one page of 100 rules, Metadata read): their pull request and required status check rules are folded into the branch rule where the strictest wins (the higher approval count, any requirement either sets, every required check), a ruleset's requirement counts as a floor while the branch rule is unreadable or the page is full, and rule types no item judges (merge queue, signatures, linear history, deployments, code scanning, workflows, update) are listed in `otherRules`. Refused rulesets read as none. The reader uses the signed-in user's token of the App, so the branch rule needs both the App's Administration read and the user's admin role on the repository; when it is refused, the branch itself (Contents read) still says whether it is protected and which checks it requires, and the rest stays `unknown`. On GitLab it is the merge request, its approvals, its approval rules (Premium: its own code owner rules; elsewhere CODEOWNERS at the base is matched, and an @name may be a group, so an owner group nobody named approved is `unknown`), the project's merge settings, at most five pages of discussions and ten of diffs. No new permission or scope is needed; nothing the token cannot read is guessed.

## Notifications

An account announces its reviews in Slack or WeCom group chats, to email addresses, or to webhooks of its own (`/api/notifications/channels`, at most 10 in all; see Outgoing webhooks). A chat channel takes the chat's incoming webhook address (`https://hooks.slack.com/services/…` or `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=…`, no other host); an email channel takes one plain address. Either is stored encrypted under `MASTER_KEY` and never answered. Each channel hears about every review, reviews with findings, or only reviews with a critical finding. A message carries the review's counts, verdict, pull request and console links, and the titles of up to three critical or warning findings when the account shares findings. The server needs outbound HTTPS to those hosts. A message that fails for a reason that may pass is tried again (see Deliveries and retries); the channel shows how its last message went, and a test message checks it.

The console's notification centre keeps, for the signed-in account, the notices of its own user, whether or not a channel hears of them: the pull request events above that concern them (`review_requested`, `pull_reviewed`, `pull_closed`, `checks_failed`, `review_blocking`, `merge_when_ready`, `stack_merge`, `pull_commented`, `mentioned`, `thread_replied`; not the reminders or `pull_at_risk`, which follow a channel's settings), and three of its own: `review_finished` (a review of a pull request stored; one its author was told of as `review_blocking` is not kept again), `automation` (a rule's notify action ran) and `job_failed` (an auto review, answer, generated draft or learning run gave up). Each is kept once per event, however often its webhook is delivered (a unique key on the account and the event), with plain text only: what happened, the pull request's title, finding titles where findings are shared, and a comment only as the short redacted excerpt its channel notice carries. `GET /api/notifications/feed?limit=1–50&before=<cursor>` lists them newest first, with the unread count (at most 100) and the cursor of the next page as `next`; `GET /api/notifications/feed/unread` answers only the count, for polling; `POST /api/notifications/feed/read` with `{"ids": [...]}` (at most 50) or `{"before": "<ISO 8601>"}` (every notice up to then) marks them read and answers the count left. Only the web session reads them. They are kept 30 days, and the account's export holds them as `notificationFeed`.

A Slack direct message channel (`"kind": "slack_dm"`) sends a member of the server's Slack workspace their notifications from the server's own Slack app. It needs `SLACK_BOT_TOKEN` (a Worker secret on the hosted Worker, `npx wrangler secret put SLACK_BOT_TOKEN`), the bot token of a Slack app installed in the workspace with the bot scopes `chat:write` (send the messages), `im:write` (open the member's direct message conversation), `users:read` (find a member by ID) and `users:read.email` (find a member by email address); without it `GET /api/notifications/channels` answers `"slack": false` and such a channel is refused. The channel takes `"member"`: the member's email address or member ID (`U…`, from their Slack profile). Only text that is no email address or member ID is refused. The server looks the member up when the channel is added (`users.lookupByEmail` or `users.info`, at most 20 lookups a day per account, then `daily_limit` with `limit` until midnight UTC; `upstream_unreachable` when Slack cannot be asked) and keeps the member's ID encrypted like a chat's address; it never answers it. Whether or not the workspace has such a member, and whether it is a bot or deactivated, the answer is the same: the channel, unconfirmed, with `last4` taken from what was typed, and `"confirmationSent": true` (false only past the confirmation cap below), meaning that if the address or ID is a person's in the workspace, they get a link. A channel whose member was not found is kept like the others and can never be confirmed; remove it to free its place, or the daily retention does (see below). Sending the link is deferred past the answer: the server opens the member's conversation with the app (`conversations.open`) the first time, keeps its ID with the member's, and posts a direct message with a link to confirm, valid for a day (`POST /api/notifications/channels/<id>/confirm` sends a new one, with the same answer; at most 10 a day per account). The member gets nothing else until the link is opened and its button pressed, so a user cannot have ocra message someone else, nor learn from ocra who is in the workspace. Each message after that is one `chat.postMessage` in that conversation, with link previews off, through the same delivery queue as the other channels, and it takes every setting a chat channel takes (which reviews, events, reminders, quiet hours, the digest and the weekly report). Slack's rate limit (an HTTP 429 or `ratelimited`), its own failures and an HTTP 5xx are tried again; any other error it names (`account_inactive`, `channel_not_found`, `invalid_auth`, a missing scope) gives the delivery up at once. On the hosted Worker the retries share the hourly run's budget for deliveries. The token, the message text and what Slack answers are never logged or kept, beyond the delivery's body until it is done (see Deliveries and retries). The server needs outbound HTTPS to `slack.com`.

Email needs `SMTP_URL` and `SMTP_FROM`; the hosted Worker has no mailer, so it refuses email channels and `GET /api/notifications/channels` answers `"email": false`. An address gets an email with a link to confirm it, valid for a day (`POST /api/notifications/channels/<id>/confirm` sends a new one; an account sends at most 10 a day), and nothing else until the link is opened and its button pressed. Every email is plain text with a simple HTML part, no images or tracking, and carries an unsubscribe link (also as `List-Unsubscribe`, for a mail client's one-click unsubscribe) that removes the address without signing in. The links are under `<PUBLIC_URL>/api/email/` and the unsubscribe links are signed with `SESSION_SECRET`: changing it invalidates those already sent.

An email or Slack direct message channel still unconfirmed 7 days after its last link was sent (or after it was added, when no link went) is deleted by the daily retention, freeing its place among the account's 10 channels; sending a new link starts the 7 days again. It goes the same way whether or not its Slack member exists, in the same daily run, so its removal says nothing about who is in the workspace. Each one is recorded in the account's audit log as `channel.expired` (the channel's ID and kind). The run makes no outbound call.

A channel can also hear about the events of the signed-in user's own pull requests on the account's enrolled repositories (`"events"` when added, or with `PATCH`; none unless set, so channels added before keep what they had): `review_requested` (a review was asked of them, or of a GitHub team they are on, or a GitLab approval rule names a group they are on (told once per merge request, whichever group): once per pull request and round of review, whether asked of them, of a team or of several, whichever ask comes first, the channel claiming one key in the database; the round ends when their review or the ask's removal ends the ask, a member's review ending a team's, so an ask after that tells them again and one from before it, delivered late or again, tells nobody; on GitLab 18.6 and later, a reviewer asked again ("re-request review", or `/request_review` of someone already a reviewer, which the merge request hook marks `re_requested` with the reviewer's state before) is told at once when they had answered since they were asked (reviewed, requested changes, approved or took an approval back), their answer ending the round just before the time GitLab wrote for the hook; asked again before they answered, they are not told twice; GitLab before 18.6 sends no hook for it, and the reviewer hears of it only from GitLab itself), `pull_reviewed` (a reviewer approved, requested changes or commented with text on a pull request they wrote; on GitLab, an approval), `pull_closed` (it was merged or closed by someone else), `checks_failed` (its pre-merge checks failed, once per head, on a server with a bot; or its CI failed on its head, once per head whatever runs after: on GitHub a check suite of another App than ocra's that completed as failure, timed out, action required or startup failure and lists the pull request at that head, on GitLab a failed merge request pipeline of an open merge request; told from the delivery alone, with no call to the platform; only the author is told, not its reviewers), `review_blocking` (ocra's review of it found a critical finding; that channel then gets this message in place of the review's announcement), `merge_when_ready` (a pull request they set to merge when ready merged or stopped; see Merge when ready), `stack_merge` (a stack merge they started merged or stopped, on any repository), `pull_commented` (someone else commented on a pull request they wrote: a comment, an inline review comment, or a review that commented with text; the inline comments of one review are one notice with the review) `mentioned` (a person's comment or review on a pull request @-mentioned their login) and `thread_replied` (someone else replied in a review thread they started). The user is known by the platform's id of their user, never by a login, except for a mention: on GitHub the account they sign in with (a mention names the login they last signed in with), on GitLab the user of the account's GitLab link and its username (a link made before either was kept must be connected again). A mention is read without a model: `@login` in any case, not inside code spans or fenced code, quoted lines, an address or a longer name, in the first 16,000 characters of the comment. A comment or review by a bot (ocra's own included) tells nobody, and a channel hears of one comment once: a mention first, then a reply in the user's thread, then the comment notice. For these three events the message quotes at most 100 characters of the comment's text, made plain (no markup, links or mentions a chat would read); comment text is never logged, nor stored beyond a delivery's record while its steps are due (see Incoming webhooks). Comment events need, beyond what auto review needs, nothing on GitHub (the App already subscribes to issue comment, pull request review comment and pull request review events) and Comments (note events) on GitLab's project hook. For `thread_replied` and `repliesWaiting` the server keeps, per enrolled repository's pull request, who started each review thread (the platform's id and login of the first comment's author) and when someone else and the starter last replied, by the platform's clock, never the text (`review_threads`, unique per repository and platform thread; the first start delivered is kept, so a redelivery changes nothing; deleted 90 days after the thread's last event, in the account's export as `reviewThreads`). On GitHub an inline review comment without `in_reply_to_id` starts a thread and a reply names it. A GitLab note names its discussion but not whether it is the first note: a plain comment (a note with no type) opens its own, and for a diff or discussion note of a discussion not on record the server reads the discussion once after answering the hook (`GET /projects/:id/merge_requests/:iid/discussions/:discussion_id`, as the bot or else the enrolling account's GitLab link, 10 seconds, at most 1 MiB, never retried) and keeps its first note's author and time as the start; with no token, a refusal or a timeout nothing is kept and a later note of the discussion tries again. Threads started by a bot are not on record, nor are GitHub threads started before the server kept them, and a reply in one tells nobody and counts nowhere; a bot's reply is not kept. An event the user caused tells nobody. The webhooks only arrive for enrolled repositories, and are read after they are answered. Each channel is told of an event once: the database keeps its key for 30 days, so a webhook delivered again sends nothing. A message names what happened, the pull request's title and a link to its page in the console under `PUBLIC_URL`; it holds finding titles only when the account shares findings.

Two of those events are reminders, which the hourly run (the Worker's `47 * * * *` cron, the Node server's hourly timer) sends once a pull request has waited the channel's `"reminderHours"` (4, 8, 24 or 48; `null`, the default, sends none): `review_waiting`, a review asked of the user that they have not given (asked again after they reviewed, it is a new reminder), and `pull_waiting`, a pull request they wrote, out of draft, that no one but its author and bots has reviewed since it was ready or reopened. Both come only from what the enrolled repositories' webhooks stored: GitHub's pull request `review_requested` and `review_request_removed` events and pull request review events, GitLab's merge request hook (reviewers added, asked again or removed, approvals; asked again, the wait starts over from the time GitLab wrote for the hook). A review asked of a GitHub team (the event's `requested_team`) is kept as the team's ask and waits for each member: one review by a member ends it, as on GitHub, and so does the team's removal; asked of the user and of their team, a pull request is reminded of once, as asked of the user, and a team's reminder names the team. GitLab has no group reviewers (a merge request's reviewers are users), but its approval rules (Premium and Ultimate) can name groups: when a merge request opens, reopens or gains commits, the server reads its approval rules once after answering the hook (`GET /projects/:id/merge_requests/:iid/approval_rules`, as the bot or else the enrolling account's GitLab link, 10 seconds, at most 1 MiB), and each group a regular or code owner rule names (at most 20; report and any-approver rules are left out) is kept as that group's ask (`team:<group id>`, named by its full path) and waits for each member like a team's: one approval by a member ends it, and so does a read of the rules that no longer names the group. A change to the rules without a push is seen at the next push. An approval GitLab takes back opens an ended ask again, as a new round its members are told of and reminded of: at the merge request hook of an approval removed (`unapproved`), and at a push, the server reads who approves the merge request now (`GET /projects/:id/merge_requests/:iid/approvals`, the same bounds, and only when an ask on it has ended) and asks again each group the rules still name whose kept members no longer include an approver. The same holds for a reviewer whose own approval ended their ask: removing it, or a push that reset it, asks them again while they are still a reviewer and the merge request is open, and they are reminded again. Each opens again in one statement that moves only an ended ask, so a hook delivered twice asks once. On GitLab Free, or when the rules are refused, nothing is asked. Merged, closed and draft pull requests are left out, and so is a wait older than seven days. Each reminder goes to a channel once (its key, the pull request and when the wait began, is kept 30 days like the events'), and a channel with several due gets one message listing them, asks of the user first, each with a link to its page under `PUBLIC_URL`. `"quietHours": {"start": 0–23, "end": 0–23}` (different hours; over midnight when end is earlier) holds a channel's reminders until the hour after them, and holds its `pull_commented`, `mentioned` and `thread_replied` notices that arrive in them: the first hourly run after they end sends the channel one message with how many there were and the newest ten, each a line with a link to its pull request (`… and N more` for the rest; up to 100 per message, the next run sends any left); a notice is held once per comment, however often it is delivered, sent once however many processes run, kept at most 48 hours (then dropped unsent), shown in the account's export as `notifyHeld`, and removed with its channel; the other events are sent at once, quiet hours or not. Quiet hours are read in the account's time zone: UTC unless set with `PUT /api/notifications/time-zone` and `{"timeZone": "<IANA name>"}` (`GET` reads it; the account's export holds it as `timeZone`). The server keeps each ask (the pull request, the platform's id of the reviewer, `team:<id>` for a team, when it was last asked and last answered) for 90 days.

Who is on a team is read when a team's ask arrives, after the webhook is answered: the copy kept for the account is used while it is younger than a day, else GitHub's `GET /orgs/<org>/teams/<slug>/members` (child teams' members included, as GitHub answers it) with an installation token of the App limited to Members: Read, or GitLab's `GET /groups/:id/members` (the group's direct members, the ones its approval rules count; active ones only) as the bot or the enrolling account's link, so at most one read per team and account a day. A read pages 100 members at a time until a page is short, ten pages at most: the first 1,000 members are kept and the rest are not reached. A page refused makes the whole answer unknown; a read the hourly run's call budget cuts short keeps nothing and is tried again with the delivery's step. Without that permission, without the App's key on the server, or on GitLab without a token that may see the group, the answer is kept as unknown for the day and the team's ask reaches nobody; nothing fails. The members are kept by their platform ids only (`review_teams`, unique per account, platform host and team; deleted 30 days after they were last read, in the account's export as `reviewTeams`); a member's review (on GitLab, approval) ends a team's ask only when the kept copy names them.

A channel set to get the daily digest (`"digest": true` when added, or with `PATCH`) receives, once a day, a summary of the account's reviews of the day before (UTC): how many, of how many pull requests, the counts by severity, the titles of up to five critical or warning findings still open when the account shares findings, and how many of the account's enrolled repositories' pull requests were merged, naming up to five, with links to the console. A day without reviews or merges sends nothing, and a channel's `"when"` holds for it too: a day without merges goes only to the channels that hear about one of its reviews (one set to blocking reviews gets it only for a day with a review that found something critical). The server checks every hour and the database records the day sent per account, so several processes on one database send it once. It needs `PUBLIC_URL`, which its links point to.

A channel set to get the weekly report (`"weekly": true` when added, or with `PATCH`) receives, once a week, a summary of the seven days before the account's report slot: a UTC weekday and hour, Monday 09:00 unless changed (`GET` and `PUT /api/notifications/report` with `{"weekday": 0–6, "hour": 0–23}`, Sunday being 0; the answer names the next slot). It holds the reviews and the pull requests they were of, the counts by severity, the findings later runs saw fixed or dismissed, and, when the account shares findings, how many of the week's findings are still open and the titles of up to five critical or warning ones; the pull requests merged, with the median time from opened to merged and the newest five; and the three repositories with the most reviews. A week without reviews or merges sends nothing, and a week without merges goes only to the channels whose `"when"` hears about one of its reviews, as for the digest. A slot is sent within a day after it, or not at all, and the database records the slot sent per account, so several processes send it once and a slot set mid-week waits for its next one. Like the digest, it needs `PUBLIC_URL`; the hosted Worker runs it from an hourly cron.

An account can also define up to 10 scheduled reports of its own (`GET`, `POST /api/scheduled-reports`; `PUT` and `DELETE /api/scheduled-reports/<id>`, by the web session only). Each has a name, a cadence in the account's time zone (the one quiet hours are read in): `"daily"` at an `"hour"` (0–23), `"weekly"` on a `"weekday"` (0–6, Sunday being 0) at an hour, or `"monthly"` on a `"monthDay"` (1–28) at an hour; the repositories it counts (`"repoIds"`, up to 50 of the account's enrolled repositories, or `null` for every review and merge of the account); its `"sections"`, any of `reviews` (how many, of how many pull requests, by severity), `outcomes` (fixed, dismissed and still open), `open_findings` (up to five critical or warning findings still open), `merged` (the pull requests merged, naming the newest five), `time_to_merge` (their median time from opened to merged) and `top_repos` (the three repositories with the most reviews), where finding titles and open counts need the account to keep findings, as for the weekly report; and `"channelIds"`, up to 10 of the account's channels, none a webhook. A report covers the time from its previous slot to this one, so a daylight saving change makes a day of 23 or 25 hours and a month is a calendar month. A slot is sent within a day after it, or not at all, and only when it came after the report was last saved; the database records each report's period (`daily:<date>`, `weekly:<its week's Monday>` or `monthly:<YYYY-MM>`, in the account's calendar) before the report is made, so several processes send it once, and moving a report's hour, weekday or day within a period does not send that period again. A period without reviews or merges in its repositories sends nothing. A report goes to each of its confirmed channels whatever their `"when"` and digest or weekly settings, as a `scheduled_report` delivery. `POST /api/scheduled-reports/preview` (a report's fields, without channels) and `POST /api/scheduled-reports/<id>/preview` answer the report for its period so far, from its latest slot to now, as text, without sending it; `POST /api/scheduled-reports/<id>/send` sends that to its channels now (at most 20 a day per account, then `daily_limit`), apart from its slots. The answer of a list or save holds each report's next slot and the newest period sent. Nothing in a report is written by a model. The periods sent are kept 90 days, and the account's export holds the reports and their periods as `scheduledReports` and `scheduledReportSends`. Like the weekly report, scheduled reports need `PUBLIC_URL`, and the hosted Worker runs them in the weekly report's share of the hourly run.

Merges come from the platforms' webhooks for enrolled repositories (see Auto review): GitHub's pull request `closed` event, through the App's webhook, and GitLab's merge request hook when a merge request is merged or closed. The server keeps one record per pull request (its title, whether it was merged, when it opened and when it closed; a later close after a reopen replaces it) for 90 days, like reviews, and the account's export holds them.

The review flow (`GET /api/insights/flow?days=7|30|90`, optionally `&repo=<full name>` of one enrolled repository) comes from the same webhooks and reads nothing from the platforms. From GitHub's pull request events (opened, ready for review, review requested, reopened, and any other for the title, author, draft state and size) and pull request review events (submitted; the App must subscribe to Pull request review), and from GitLab's merge request hook (open, update with a new reviewer or out of draft, reopen, and approval), the server keeps one record per pull request: its title, author, size where GitHub says it (lines added plus deleted), whether it is a draft, and when it opened, became ready for review, was first asked for a review, first reviewed and first approved, the earliest delivery winning. It also keeps each review once, by reviewer and whether it approved; on GitLab an approval is the review, once per approver. A review by the author or by a bot is not counted. The answer holds pull requests opened and merged per UTC week, the median and 90th percentile from ready for review to the first review and to the first approval and from the first approval to the merge, the five open pull requests waiting longest for a first review, reviews per reviewer, and pull requests opened by size. Pull requests from before a repository was enrolled are not there. Records go 90 days after their last event, reviews 90 days after they were submitted, and the account's export holds both.

Reviewer workload (`GET /api/insights/reviewers?days=7|30|90`, optionally `&repo=<full name>`) reads the same records and the reviews asked of each reviewer (GitHub's review requested and removed events, GitLab's merge request hook), and nothing from the platforms. Per platform login (no other detail of a person) it answers the reviews submitted in the window, the asks made of them in it, the median and 90th percentile from an ask to their first review after it, the asks that wait now on open pull requests out of draft, and the pull requests they opened; per UTC week, the median and 90th percentile from an ask to its review, by the week of the review, and how many pull requests out of draft spent part of the week more than 24 hours past ready for review without a first review. An ask is kept by the reviewer's platform id, with the login when the event names it; asks recorded before logins were kept have none and are left out, and so are a team's asks.

Review targets set how soon an enrolled repository's pull requests should get a first review and be merged: `PUT /api/review-targets/default` with `{"firstReviewHours": 1–720 | null, "mergeDays": 1–90 | null}` sets the account's default, `PUT /api/review-targets/repos/<enrolled repository id>` with the same body a repository's own in its place (a `null` there sets none of that kind for it), `DELETE /api/review-targets/repos/<id>` returns it to the default, and `GET /api/review-targets` reads them all; none is set until then, and a repository's own go when it is removed. `GET /api/insights/at-risk` (optionally `?repo=<full name>`) lists the open pull requests out of draft, with an event in the last 90 days, near a target (three quarters of it passed) or past it, past first, then the earliest due, at most 200: each with the target (`first_review`, counted from when it was ready for review or last reopened, until its first review; `merge`, from when it was ready, until it is merged), when it started and is due, and the logins asked for a review who have not given one. It reads only what the webhooks stored (pull request events, reviews, review requests, closes), never the platforms; a pull request whose close the server never heard of stays open to it until the daily reconciliation (above) fills it in. A channel that hears about `pull_at_risk` is told by the hourly run, in one message per channel naming up to ten, when a pull request comes near or past a target: once per pull request, target and start however many processes run it (a changed target does not tell it again; a reopen starts a new first-review clock), held in its quiet hours until they end, and never for one that came near its target more than seven days before. The targets are in the account's export as `reviewTargets`.

What ocra changed (`GET /api/insights/impact?days=7|30|90`, optionally `&repo=<full name>` of an enrolled repository or one reviewed in the window) reads only stored rows, nothing from the platforms, in total, per UTC week and per repository the account reviewed pull requests of, enrolled or not (`enrolled` on each row): in an enrolled repository, the pull requests opened in the window (from the same webhook records) and how many of them ocra reviewed; in any other, which has no such records, the pull requests ocra reviewed in the window, each counted once in the week of its first review in it; ocra's reviews of pull requests made in the window (a review names its pull request by the repository's address and number, as the CLI uploads it; local reviews are left out), their findings by severity, and the earlier findings those reviews counted as fixed in the code or dismissed by a reviewer; while the account shares findings, how many of those reviews' findings are marked fixed on the console, dismissed, still open, or have an issue opened from them, and how many have the thread of ocra's comment resolved from the console, counts only, never their text (`actedOn` is null otherwise). `actedOn.fixedVia` splits the fixed ones by how they became fixed, recorded in the same write that marks them fixed and only by the first: `applied` (ocra's fix committed from the pull request's page), `suggestion` (the suggested change in ocra's comment applied from its threads, matched by the finding marker the comment carries), `manual` (marked by hand), `rereview` (a later review of the same pull request uploaded, while the account shares findings, the finding's fingerprint among the earlier findings it saw fixed, at most the contract's 200; only a finding still open, addressed or merged is marked, so one marked fixed or dismissed keeps its fate; the findings it saw dismissed by a reviewer on the platform are not recorded, since a dismissal on the console always names a reason and the platform's names none) and `unknown` (fixed before migration 0060 kept the source). Resolving a thread sets neither fixed nor dismissed, since a thread is resolved either way: a person resolving the thread of ocra's comment, from the console or on the platform (GitHub's `pull_request_review_thread` event; on GitLab, read from the discussion when a person writes in it), makes the finding `addressed` (`actedOn.addressed`) while it is open, and reopening it makes it open again. When an enrolled repository's pull request merges, its findings still open become `merged` (`actedOn.merged`: merged unaddressed, since no fix was seen); a fix a later review sees still makes an addressed or merged finding fixed, and a pull request closed without merging leaves them open, since it may be reopened. Neither is a decision the inbox takes (`POST /api/findings/decide` answers 400), and migration 0100 made the open findings whose threads were resolved before this addressed. For the enrolled repositories' pull requests merged in the window (`toMerge`, null when no enrolled repository is in scope, since only the webhooks record merges) it answers the median and 90th percentile from ocra's first review to the merge, and from opened to the merge for those ocra reviewed before the merge and for those it did not. A suggestion applied on the platform itself is not seen (nothing is polled), nor is a suggestion applied from the console that is not in ocra's comment.

### Deliveries and retries

Every message to every kind of channel is a delivery: a review's announcement, a pull request event, a reminder, a rule's notice, the daily digest, the weekly report, the notices held in quiet hours, and a test message (`ping`). The digest and the weekly report are claimed once per account and day or week before they are made, and then delivered to each channel like any other message, so a chat that is down when they go still gets them. A delivery keeps its id on every attempt (a webhook's `ocra-delivery` header). An attempt that may go otherwise later is tried again after 1 minute, 5 minutes, 30 minutes and 2 hours (five attempts in all) with the same body; anything else ends it at once:

| Kind | Tried again | Given up |
|---|---|---|
| Slack | no answer, a timeout, a 408, 429 or 5xx | Slack answering `invalid_token`, `invalid_auth`, `no_service`, `no_service_id`, `no_team`, `team_disabled`, `channel_not_found`, `channel_is_archived`, `action_prohibited`, `posting_to_general_channel_denied`, `invalid_payload` or `no_text`, whatever the status; any other status; a redirect |
| WeCom | no answer, a timeout, a 408, 429 or 5xx; a 200 with `errcode` -1 (busy) or 45009 (rate limit) | any other `errcode` (`rejected`); any other status; a redirect |
| Email | no connection, a timeout, an SMTP 4xx reply | an SMTP 5xx reply; a server that takes no recipient (`rejected`) |
| Webhook | no answer, a timeout, a 408, 429 or 5xx | any other status; a redirect; a refused address |

Each attempt opens the channel's address again, so a channel removed (or unsubscribed from) takes its deliveries with it, and one whose address no longer decrypts, or an email channel on a server that no longer has a mailer, is given up as `refused`. The Node server's retry loop runs every minute; the hosted Worker retries from its hourly cron, so there a retry waits for the hour, within its share of the run's calls ([The hourly run's calls](#the-hourly-runs-calls)). Each attempt is taken by one process (a compare-and-set on the delivery, with a two-minute lease), so several processes send it once at a time. A sweep tries at most 50, going round the channels with deliveries due one at a time, so one address that keeps failing cannot hold up the others. A review's announcement, a digest and a weekly report remember which settings of the channel's `when` take them: when a retry is due after the channel's `when` was narrowed to one that no longer takes it (from every review to critical findings only, say), it is given up as `unwanted`, not sent, and stays in the channel's deliveries; the channel's last status is left as it was. Test messages, pull request events and held notices do not depend on `when`.

`GET /api/notifications/channels/<id>/deliveries` lists any channel's newest 20 deliveries, the console's Deliveries drawer: event (a webhook event, or `digest`, `weekly_report` or `held_notices`), state (`pending`, `delivered`, `failed`), attempts, the last status (the HTTP status, or the SMTP reply code for email), why it failed (`refused`, `redirect`, `timeout`, `network`, `status`, `rejected`, or `unwanted` for a retry the channel's `when` no longer takes), latency, the next attempt's time and when it was made, never a body or what came back. Only the channel's own account sees them; another account's channel answers 404. The body (what is sent, without the address: a chat's JSON, an email's subject, parts and headers, a webhook's JSON) is stored only while a retry is due and cleared once the delivery is delivered or given up, and a channel keeps only its newest 20 deliveries, so an older one still waiting for a retry is given up; records go after 30 days or with their channel, and the account's export holds them as `notifyDeliveries`. No log line holds a body, an address, a URL or a secret.

### Outgoing webhooks

A channel of kind `webhook` posts each event as JSON to an endpoint of the account's own: `{"kind": "webhook", "name": …, "when": …, "url": "https://…", "events": […], "reminderHours": …}`. The address must be `https`, without credentials or a fragment, on port 443 or one above 1023, and name a public host: the server takes the URL as `new URL()` normalises it (so `https://2130706433/` is `127.0.0.1`) and refuses loopback, private, shared (`100.64.0.0/10`), link-local (`169.254.0.0/16`, the cloud metadata address included), documentation, multicast and reserved IPv4 addresses, every IPv6 address outside global unicast (`::1`, `fc00::/7`, `fe80::/10`, IPv4-mapped, 6to4, Teredo), names without a dot or with an empty label (`localhost..`), and `localhost`, `metadata.google.internal` and names under `.localhost`, `.local`, `.internal`, `.lan`, `.home.arpa` or `.onion`. A Node server also checks every address the name resolves to, in the lookup its connection uses, so a name that resolves, or rebinds, to such an address is refused before it connects; the hosted Worker cannot resolve names itself, and Cloudflare's network does not route to private addresses. A redirect is never followed (it fails the delivery), an attempt waits at most 10 seconds, and at most 4 KiB of the answer is read and dropped: only its status and how long it took are kept.

When the channel is added the answer holds `"secret"`, the key its deliveries are signed with, shown only then; `POST /api/notifications/channels/<id>/secret` replaces it and answers the new one once, and the old one stops signing at once. It is stored encrypted under `MASTER_KEY` with the address, like a chat's. A webhook channel takes no digest, weekly report or quiet hours (they are for people; the server refuses them with 400): it gets each event when it happens. It hears about reviews by its `"when"` (`review_completed`), the events of the user's own pull requests and reminders it subscribes to as above, an automation rule's notify action (`automation_ran`), and `ping` from `POST /api/notifications/channels/<id>/test`.

Each delivery is a `POST` with these headers:

| Header | Value |
|---|---|
| `content-type` | `application/json` |
| `user-agent` | `ocra-webhooks/1` |
| `ocra-event` | the event, as in the body |
| `ocra-delivery` | the delivery's id, the same on every retry: use it to drop a repeat |
| `ocra-timestamp` | when this attempt was signed, in seconds since the epoch |
| `ocra-signature` | `sha256=` and the hex HMAC-SHA256, under the secret, of the timestamp, a `.` and the raw body |

To verify one, recompute the signature over the raw bytes received, compare it in constant time, and refuse a timestamp more than five minutes from your clock (a replayed delivery):

```js
import { createHmac, timingSafeEqual } from "node:crypto";

function verify(secret, headers, rawBody) {
  const ts = Number(headers["ocra-timestamp"]);
  if (!Number.isInteger(ts) || Math.abs(Date.now() / 1000 - ts) > 300) return false;
  const want = `sha256=${createHmac("sha256", secret).update(`${ts}.${rawBody}`).digest("hex")}`;
  const got = String(headers["ocra-signature"] ?? "");
  return got.length === want.length && timingSafeEqual(Buffer.from(got), Buffer.from(want));
}
```

The body is versioned (`"version": 1`; a field may be added within a version, never removed or changed):

```json
{
  "version": 1,
  "id": "<delivery id>",
  "event": "review_completed",
  "createdAt": "2026-11-23T09:00:00.000Z",
  "data": {
    "review": { "id": "…", "consoleUrl": "…", "verdict": "significant_concerns", "complete": true,
                "critical": 1, "warning": 0, "suggestion": 2 },
    "pull": { "platform": "github", "repo": "octo/api", "number": 7, "consoleUrl": "…" },
    "findings": [{ "severity": "critical", "title": "…", "file": "src/db.ts" }]
  }
}
```

`data` by event:

- `review_completed`: `review` as above; `pull`, or `null` for a review of no pull request on a configured platform; `findings` (at most 50, model titles made plain, and the file) only while the account shares findings, otherwise absent.
- `review_requested`, `pull_reviewed`, `pull_closed`, `checks_failed`, `review_blocking`, `merge_when_ready`, `stack_merge`, `pull_commented`, `mentioned`, `thread_replied`: `pull`, and `summary`, what happened in ocra's own words (it may name the login of who did it); `review_blocking` adds its critical `findings` while the account shares them. The pull request's title and a comment's text are not sent.
- `review_waiting`, `pull_waiting`: `pulls`, each a `pull` with its platform `title` (or `null`) and `waitingSince`; one delivery per kind per hourly run.
- `pull_at_risk`: `pulls`, each a `pull` with its `title`, `target` (`first_review` or `merge`), `state` (`near` or `past`) and `due`.
- `automation_ran`: `rule`, the rule's name made plain, and `pull` (or `null`).
- `ping`: `message`.

No body holds code, a finding's text or suggestion, or a secret. A delivery is retried as Deliveries and retries says, with the same id and body and a new timestamp and signature on each attempt.

## Ask ocra

The review page answers questions about one review and its pull request ("why is this finding critical?", "what does this change do?"): `GET /api/reviews/<id>/chat` reads the conversation, `POST` with `{"message": "…", "model"?: "ocra-<provider>/<model>"}` asks, and `DELETE` clears it. Only a web session asks. A question goes to the model it names, or to the account's standard model (Defaults), or its top or light one when that is unset, and the call is made with the account's own key for that provider, or the server's key for a `MODEL_ENDPOINTS` entry that has one; with none, it is refused (`no_key`). The provider must have an OpenAI-compatible chat route, or else Anthropic's messages route.

Data flow, one question:

1. The server reads what it holds for the review: its counts, verdict and pull request, and, while the account shares findings, the findings' text and the walkthrough (both already redacted on upload). When the account does not share findings the model is told so, and says so when a question needs them. When the account has a connection to the pull request's platform, the pull request's files and diff are read then, as the user, with the same calls as the pull request's page; nothing read is stored. The diff may be of a newer head than the one reviewed, and the prompt says when it is.
2. The prompt holds ocra's instructions, then that data in sections tagged with a random nonce made for the request, so text from the change cannot close a section; any `<ocra` or `</ocra` in the data is defanged as the engine's `data()` does, and control characters are dropped. Each field is cut (findings at 50, a diff at 48,000 characters), the question at 4,000 characters, and the 20 latest messages go with it.
3. The call counts against the gateway's daily cap and the account's budget, in the statement that checks them, and is recorded as a gateway call (provider, path, model, status, tokens, time), as one through `/api/gateway` is. The prompt and the answer are never logged.
4. The answer streams back as server-sent events (`delta`, then `done` with the stored message, or `error`), on Workers and on Node alike, and is cut at 16,000 characters. The question and the answer are stored in `review_chat_messages`; a question that got no answer is removed.

A review keeps at most 100 messages, checked in the statement that adds one; clearing the conversation makes room. The messages are deleted with their review, by the user or after 90 days, with the account, and when the account stops sharing findings and deletes what it shared; the export holds them.

The pull request page asks the same way about the pull request itself, without opening a review: `GET /api/pulls/chat?platform=&repo=&number=` reads its conversation, `POST /api/pulls/chat` with `{"platform", "repo", "number", "message", "model"?, "finding"?, "file"?}` asks, and `DELETE` with the same query clears it. A question may name one of the pull request's findings (by id; a finding of another pull request is refused) or one of its files (by path), and the prompt then puts that finding, or that file's diff, in a focus section ahead of the rest. The pull request's diff is always read, as the user, and the question is refused (`not_found`) when the platform does not show it to them; the review data is ocra's newest review of the pull request, at any head. The call goes through the same model path, cap, budget and gateway record as above. Questions (with the finding or file they were about) and answers are stored in `pull_chat_messages` by pull request, at most 100 each; they are deleted after the retention period (90 days unless `RETENTION_DAYS` says otherwise), with the account, and when the account stops sharing findings and deletes what it shared; the export holds them.
