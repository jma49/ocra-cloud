# Self-hosting ocra Cloud

A company GitLab with its own models, end to end: [gitlab.md](gitlab.md).

The same API and web app as app.ocracloud.com, on Node with Postgres or a SQLite file instead of Cloudflare Workers and D1. `src/node/` is the only code that differs: it opens Postgres or libSQL, reads the client's address from the socket or a trusted proxy, keeps the rate limits in memory, runs the daily retention, and serves `web/dist`. `test-node/` runs the app this way in CI.

## Run it

With Docker Compose, on one machine: the server, and Caddy in front of it ending TLS (`selfhost/`).

```sh
cd selfhost
cp .env.example .env            # OCRA_DOMAIN, OCRA_TLS
cp ocra.env.example ocra.env    # the server's variables, below
docker compose up -d
```

`OCRA_TLS` says where the certificate comes from: `internal` (Caddy's own CA, for a trial), an email for a public name that Let's Encrypt can reach, or `/certs/<cert>.pem /certs/<key>.pem` with the company's certificate placed in `selfhost/certs/`. Compose sets `PUBLIC_URL` and `TRUSTED_PROXY_HOPS` for you. Data lives in the `ocra-data` volume.

Behind your own load balancer instead, run the image alone:

```sh
docker build -t ocra-cloud .
docker run -p 8787:8787 -v ocra-data:/data --env-file ocra.env ocra-cloud
```

Without Docker: `npm ci && npm run build:web && npm run build:node`, then `node dist/server.mjs` with the variables below. Migrations are applied at start.

## Variables

| Variable | Required | Meaning |
|---|---|---|
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | one way to sign in | Your own GitHub App's client, with expiring user tokens and the repository permissions Contents and Pull requests set to read and write (the console comments, reviews, merges and commits a finding's fix as the user); its callback URL is `<PUBLIC_URL>/api/auth/github/callback` |
| `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` | one way to sign in | An OpenID Connect provider: the company's SSO (Keycloak, Azure AD, Okta) or a self-hosted GitLab, which is one. A confidential client with the scopes `openid profile email` and the redirect URI `<PUBLIC_URL>/api/auth/oidc/callback`; the issuer is the URL its discovery document names, such as `https://gitlab.example.com`. With the same client and address as `GITLAB_CLIENT_ID` and `GITLAB_URL`, the sign-in also asks for `api` and connects GitLab (gitlab.md) |
| `OIDC_NAME` | no | the provider's name on the sign-in button, "SSO" when unset |
| `MASTER_KEY` | yes | base64 of 32 random bytes (`openssl rand -base64 32`); wraps every stored key. Losing it loses them |
| `MASTER_KEY_PREVIOUS` | during a rotation | as on Workers (`docs/rotation.md`) |
| `SESSION_SECRET` | yes | signs the sign-in state cookie |
| `GITLAB_CLIENT_ID`, `GITLAB_CLIENT_SECRET` | to connect GitLab | a GitLab OAuth application (scope `api`: the console comments, approves and merges as the user); its redirect URI is `<PUBLIC_URL>/api/platforms/gitlab/callback` |
| `GITLAB_URL` | for a self-hosted GitLab | the instance, such as `https://gitlab.example.com`, or `https://example.com/gitlab` for one installed under a relative URL root; `https://gitlab.com` when unset |
| `PUBLIC_URL` | behind a TLS proxy | the address people open, such as `https://ocra.example.com` |
| `TRUSTED_PROXY_HOPS` | behind a proxy | how many proxies in front append to `X-Forwarded-For` (1 for one TLS proxy); the login code limits count by the address read past them. 0, the socket's peer, when unset |
| `MODEL_ENDPOINTS` | for company models | the company's own OpenAI-compatible model endpoints, as JSON (Company models below) |
| `DEFAULT_MODELS` | no | the default models, as JSON (`{"top": ["ocra-corp/qwen3-coder"], "light": "ocra-corp/qwen3-8b"}`), that an account starts with until it saves its own; each must be one the gateway serves |
| `BUILTIN_PROVIDERS` | no | `off` forwards to `MODEL_ENDPOINTS` only, never to the public providers; `on` when unset |
| `GITHUB_WEBHOOK_SECRET` | for GitHub code graphs | your GitHub App's webhook secret; the App's webhook URL is `<PUBLIC_URL>/api/webhooks/github` (`/api/graphs/webhooks/github`, its earlier address, still answers), subscribed to push and pull request events. The App's webhooks are refused without it |
| `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY` | for GitHub auto review | your GitHub App's id and private key (PEM; `\n` for line breaks on one line). Each review gets an installation token limited to its repository; the App needs Contents read, Pull requests read and write, Checks read and write (for pre-merge checks), and the pull request, pull request review, issue comment and pull request review comment webhook events |
| `GITLAB_BOT_TOKEN` | for GitLab auto review | a bot account's token (scope `api`), which posts the reviews |
| `AUTO_REVIEW_WORKERS` | no | reviews at once in this process (default 1; 0 only queues them for another process on the same database) |
| `GRAPH_WORKERS` | no | code graph builds a process runs at once, each of another repository; 1 when unset |
| `CODE_GRAPH` | no | what the server does with code graphs: `keep` (the default), `opt-in` (only for repositories added with the owner's consent) or `off` (none kept; the daily retention deletes any that are) |
| `DATABASE_URL` | no | a Postgres server's `postgres://user:password@host:5432/db`, or a libSQL URL: `file:/data/ocra-cloud.db` in the image, or a libSQL server's |
| `RATE_LIMITS` | with several processes | `database` counts the rate limits in the database, so that each holds for the deployment; `memory`, per process, when unset |
| `MIGRATE` | with several processes | `on` (the default) applies the migrations at start, `off` leaves them, `only` applies them and exits |
| `SMTP_URL` | for email notifications | the mail server, as `smtp://user:password@host:587` (STARTTLS when the server offers it) or `smtps://user:password@host:465`; without it email channels are refused |
| `SMTP_FROM` | with `SMTP_URL` | the address email is sent from, such as `ocra@example.com` |
| `NODE_EXTRA_CA_CERTS` | for a company certificate authority | its certificate (PEM), which the server and each review's CLI then trust; git reads the system's store or `GIT_SSL_CAINFO` (gitlab.md, Certificates and proxy) |
| `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` | behind a proxy | passed, with the certificate variables, to each review's git and CLI |
| `PORT` | no | 8787 |
| `GATEWAY_DAILY_CALLS`, `REVIEW_DAILY_UPLOADS`, `REVIEW_MAX_FINDINGS`, `DEVICE_DAILY_CODES`, `DEVICE_DAILY_CODES_PER_NETWORK` | no | the Worker's defaults (`wrangler.jsonc`) |

Serve it over HTTPS: session cookies are `__Host-` cookies, which browsers keep only on secure origins.

## Company models

`MODEL_ENDPOINTS` declares the company's own model endpoints, such as an internal gateway in front of vLLM or a hosted model, as a JSON list:

```json
[
  {
    "id": "corp",
    "label": "Corp LLM",
    "base": "https://llm.corp.example/openai",
    "models": "/v1/models",
    "key": "the server's key for it"
  }
]
```

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | lowercase letters, digits and `-`, not a built-in provider's id; models are named `ocra-<id>/<model>`, such as `ocra-corp/qwen3-coder` |
| `label` | yes | the name the console shows |
| `base` | yes | an http or https URL without credentials, query or fragment; the paths are appended to it |
| `paths` | no | the paths the gateway forwards, `["/v1/chat/completions"]` when unset; the CLI needs one ending in `/chat/completions` |
| `auth` | no | `bearer` (the default) or `x-api-key`: how the key goes on the request |
| `models` | no | a GET that lists the models in OpenAI's shape; it also checks a key |
| `key` | no | the server's own key: every account's calls use it and nobody stores one. Without it, each person adds their own key for the endpoint on the keys page |

With `DEFAULT_MODELS` naming them, a colleague who signs in for the first time reviews with the company's models without setting anything. The endpoints appear in the console's "Your company" group, and the CLI reaches them through the gateway like any other provider, with the same metering and daily caps. A declaration the server cannot read stops it from starting, naming the field. Keep the filled-in environment file secret when it holds a `key`.

## Postgres

For a team, keep the data in Postgres (13 or later): `DATABASE_URL=postgres://…`. With Compose, `docker-compose.postgres.yml` runs Postgres 17 in a container beside the server, its data in the `postgres-data` volume:

```sh
echo "OCRA_DB_PASSWORD=$(openssl rand -hex 24)" >> .env
docker compose -f docker-compose.yml -f docker-compose.postgres.yml up -d
```

A one-off `migrate` run applies `migrations-pg/` before the server starts. To use the company's own Postgres instead, leave that file out and set `DATABASE_URL` in `ocra.env`. The tables and values are those of the SQLite schema: times are milliseconds in `bigint` columns, JSON is text. Back up with `pg_dump`.

## Several processes

`docker-compose.replicas.yml` runs several ocra processes on this machine against its database, behind the same Caddy:

```sh
docker compose -f docker-compose.yml -f docker-compose.replicas.yml up -d
```

A one-off `migrate` run (`MIGRATE=only`) applies the migrations first; the replicas (`OCRA_REPLICAS` in `.env`, 2 by default) start after it with `MIGRATE=off` and `RATE_LIMITS=database`. Caddy sends requests to each in turn and skips one that fails its health check. The SQLite file runs in WAL mode, so readers do not wait for the writer. For processes on several machines, point `DATABASE_URL` at Postgres (add `-f docker-compose.postgres.yml` here) or a libSQL server, with the same two settings.

## Code graphs

An account adds a repository on the console's Code graphs page (or `/api/graphs/repos`); the server then keeps a graph of its default branch (symbol names, kinds and line numbers per file, never code), built after each push from the platform's tree and blob APIs with the account's own token, reading only the files that changed. Pushes arrive at `<PUBLIC_URL>/api/webhooks/github` (the GitHub App's webhook, signed with its secret) or `/api/graphs/webhooks/gitlab` (a project hook with the secret the server answers when the project is added). Builds older than 14 days are deleted daily, except each repository's newest; an account rebuilds a repository's graph from its branch's head, purges its graphs or removes it at any time, from the same page. The page is in the console only where `CODE_GRAPH` is not `off`. Builds run in the server process with the engine's tree-sitter parser (`@open-cr-agent/code-graph`); with several processes on one database, each build is claimed by one of them. `PUBLIC_URL` must be set for GitLab, whose token refresh names the server's address.

The pull request inbox (`GET /api/platforms/pulls`) reads, live as the user, the pull requests asking their review, theirs open and theirs merged in the last week, with their labels and the verdict of the account's newest ocra review of each (`blocking` when it is `significant_concerns`). An account names up to 20 sections of it (`/api/pull-views`: list, add, `PUT /<id>` to rename, change, move or hide, `PUT /order` with every id, `DELETE /<id>`), each filtering by repository, author (me, others or logins), review state, draft, checks, verdict, label and days since the last update; names are unique per account. An account without sections is offered four defaults, which `POST /api/pull-views/defaults` keeps so they can be changed. `?group=views` also answers each visible section with the pulls it holds, evaluated on the server over the same listing.

Each listed pull request is `unread` when it changed since the account last saw it, with the first `unreadReason` that holds (`new`, `marked`, `commits`, `merged`, `ocra_review`, `activity`), from the listing's `updatedAt` and head and the account's newest ocra review; no other platform call is made. The server keeps one read mark per pull request (platform, repository, number, the platform's `updatedAt` and head the user saw, and when), which never moves to an older `updatedAt`. The pull request page marks its pull request read with `POST /api/pulls/seen` (`platform`, `repo`, `number`, `updatedAt` and `head` from `GET /api/pulls/files`), and `POST /api/pulls/seen/bulk` marks up to 250 read (`read: true`, each with its `updatedAt` and `head`) or unread (`read: false`). A pull request with no mark is read when its `updatedAt` is at or before the account's inbox baseline, and otherwise unread (`new` when it was opened after it): the baseline is when the account first listed its inbox, kept from then on, and never earlier than 90 days ago, so a new account starts with nothing unread and a mark that expires leaves its pull request read. Marks go 90 days after they were last set, and the account's export holds them and the baseline (`inboxSince`).

A pull request's page reads its diff live as the signed-in user (`GET /api/pulls/files`, at most 4 MB of diff per page) and sends their comment, review and merge to the platform as them (`POST /api/pulls/comment`, `/review`, `/merge`); only a web session may, and nothing read or sent is kept. A review or merge names the head commit the user read, and one that moved since answers `head_moved` instead of acting. GitLab takes approve and comment as verdicts, and merge or squash as merges. A review shared with its findings also keeps its walkthrough (overview, files in groups, diagram), redacted again on the server, on the review's page and in its export. A finding has a fix when the CLI shared one (0.10.0 and later) and the server's own redaction left its replacement whole. That fix is committed to the pull request's branch with `POST /api/pulls/apply-fix`, as the user, only while the pull request is still at the commit that was reviewed and the file is unchanged since; the finding is then marked fixed. Cycle time (`GET /api/insights/cycle?platform=…&days=…`, optionally `&repo=…` for every author's pull requests in one repository) reads up to 50 pull requests merged in the last 90 days at most, as the user, and times each from opened to the first review or comment by someone else and to merged; nothing is kept.

The page also suggests up to five reviewers (`GET /api/pulls/reviewers?platform=&repo=&number=`), read as the user and kept nowhere: the owners the repository's CODEOWNERS at the pull request's base gives its changed files (at most 300; GitHub's `.github/`, root and `docs/` locations, GitLab's root, `docs/` and `.gitlab/`, at most 128 KB; the last matching rule wins, per section on GitLab, and teams, groups, roles and emails are listed as owners but not expanded), and, for a repository the account enrolled, who reviewed its pull requests in the last 90 days. Which paths those reviews touched is not kept, so history ranks by reviews of the repository as a whole. Each suggestion says why, how many changed files it owns, its recent reviews and how many open pull requests ask it for a review now as the user sees them, which lowers its rank; the author and bots are left out. `POST /api/pulls/reviewers` with `platform`, `repo`, `number` and up to 10 `logins` asks them for a review as the user.

A repository's learnings (`.ocra/learnings/*.md`, ADR-0037 of the engine) are read live at its default branch as the signed-in user (`GET /api/learnings?platform=…&repo=…`, 50 files a page, `&after=<id>` for the next), parsed as a review would read them; files a review would skip are listed with the reason. `GET /api/learnings/proposals` lists the open pull requests from the repository's own `ocra/learnings-*` branches (at most 10) with the learnings each adds, changes or deletes. An addition, edit or deletion (`POST /api/learnings`, `POST /api/learnings/delete`) is committed as the user on a new `ocra/learnings-*` branch and opened as a pull request, or committed on the default branch with `direct: true` when the platform lets the user; it names the file's blob as the console read it, and a file changed, added or deleted since answers `conflict` instead of being overwritten. Only a web session may, and nothing read is kept. Each learning listed comes with how many of the repository's uploaded reviews were given it in the last 90 days, and when the newest was (`usage`), from the learning ids a review uploads with a pull or merge request, or with its findings.

A repository's committed review configuration, `.ocra/config.json` and its rules in `.ocra/rules.json`, is read and changed the same way. `GET /api/repo-config?platform=…&repo=…&file=config|rules` (`config` when left out) answers the file's text at the default branch, its parsed value or why it is not JSON, its blob (`null` when there is no file), what the engine would refuse in it (`errors`, at most 20), and the `$id` of the JSON Schema an editor can check it with (`schema`; the rules file has none). `POST /api/repo-config` with `{ platform, repo, file, text, expected, direct? }` commits the text as the user on a new `ocra/config-*` branch opened as a pull or merge request, or on the default branch with `direct: true` when the platform lets the user; `expected` is the blob the edit was made on (`null` for a file that must not exist yet), and a file changed since answers `conflict`. Text that is not JSON, is over 64 KiB, or does not fit the engine's schema is refused with `invalid_body` and its `issues` (paths under `text`) before anything is sent. The schemas are the engine's (`src/engine-schemas.ts`, made from the pinned `@open-cr-agent/cli` and `core` by `node scripts/engine-schemas.ts`; a test fails when they drift); the configuration's JSON Schema leaves out a few checks the CLI makes again when it loads the file (endpoint addresses, credential variable names, unique merge check ids), so a review can still refuse a file the console accepted. The console adds nothing the file could not already say: what a review runs from it is the engine's decision, as for a file committed by hand.

A pull request's impact (`/api/graphs/repos/<id>/impact?pull=<number>`) is computed from that graph on request: the platform's pull request API gives the changed files' hunk headers, the symbols the hunks touch on the graph's side are the changed ones, and their uses are the other files' identifiers of the same name, matched by name and not type-resolved. The code line of up to 40 uses is read from the platform at the graph's commit for the answer and not kept. The review page of a pull request's review shows it in a rail beside the findings when the console keeps a graph of that repository; a review uploaded before this server stored pull requests (migration `0028`) has none.

## Limits of this first version

- Set GitHub, OpenID Connect or both; the server refuses to start with neither. An account belongs to the identity it signed in with: the same person through GitHub and through SSO is two accounts.
- Back up the `/data` volume, or the Postgres database; there is no Time Travel as on D1.

## Auto review

With a bot's credentials and `PUBLIC_URL` set, the server reviews pull requests itself (ADR-0046 of the engine): an account enrolls a repository (`/api/auto-review/repos`; one account per repository, whose models, keys, budget and rules the reviews use), and a pull request is queued when it opens, reopens, leaves draft or gains commits. GitHub's events come through the App's webhook (`/api/webhooks/github`), GitLab's through a project hook to `/api/auto-review/webhooks/gitlab` with the secret the server answers when the repository is enrolled (tick Merge request events; they also carry the approvals the review flow counts). A newer head supersedes a queued one, and one pull request is reviewed once at a time. On a pull request's page, the enrolling account can also ask for a review now (`POST /api/pulls/review-now` with `platform`, `repo` and `number`; `GET` with the same query answers the newest one): the server reads the pull request as the user and queues its current head, whatever head the request names, once; a head with a queued or running review answers that review, and a head already reviewed is reviewed again only with `force: true`. A person asked for it, so automation rules that skip reviews do not apply. A server without a runner, such as Cloudflare Workers, answers `not_found`.

Each review clones the repository into a new temporary directory and runs the installed `ocra` CLI there, as CI does: `ocra review --pr <n> --publish --no-repo-config` (`--mr` on GitLab), signed in to this server as the enrolling account through a session made for the run. Nothing from the pull request runs. It posts as the bot, and gets only the variables it needs, none of this server's secrets: those of the certificate authorities and the proxy are passed on. The directory and the session are removed when the run ends, whatever its outcome; a failed run is retried twice, five and ten minutes later. The image includes git; a server run outside it needs git on its `PATH`.

A comment that mentions `@ocra` on an enrolled repository's pull request, written by a person (never a bot), queues an answer, once per comment: `ocra reply --pr <n> --comment <id>` (`--inline` for a review comment, `--mr` on GitLab) runs the same way, and the CLI answers in the comment's thread or decides there is nothing to answer. GitHub sends these as the App's issue comment and pull request review comment events; on GitLab, tick Comments (note events) on the same project hook. A failed answer is retried like a review.

## Automation rules

An account sets up to 50 rules (`/api/automations/rules`), each a set of conditions that must all hold and the actions taken when they do. A `queued` rule runs when a pull request of an enrolled repository is queued for review, and can match the repository, the author (on GitLab known only when the merge request opens), the base branch, a title pattern (`*` and `?`) and labels. A `reviewed` rule runs when a pull request's review is uploaded, and can match the repository, a critical finding and the verdict. Either can match the changed files: include and exclude globs read as `.gitignore` reads them (`*`, `?` and `**`, case ignored, at most 20 of each), held when at least one changed file, or with `every` each of them, is included and not excluded. The files are read from the platform when the rule is tried, as the bot or else the account's link, at most 300 of them; a rule they cannot decide (unreadable, or more files than that) is logged as skipped with its reason, never as matched. The actions add labels, request reviewers and post a plain comment as the ocra bot, notify one of the account's channels, or skip the review (`queued` only). The bot writes only on repositories the account enrolled, and only on a server with a bot: elsewhere those actions are kept and logged as needing a self-hosted server. A `queued` rule acts when the pull request opens, reopens or leaves draft; on a push only its skip applies. Each rule runs once per event, `/api/automations/dry-run` says which rules match a described pull request, and `/api/automations/runs` lists what each run did, kept for 30 days. A bot write the platform did not answer (a timeout, a 5xx or a 429) is tried again a minute and then five minutes later, three attempts in all, by the server's loop (a run shows its `attempts` and, while one is due, `retryAt`); a refusal is not. `/api/automations/dry-run` takes the changed files as `paths`, and names a rule on paths it was given none for as skipped.

## Pre-merge checks

An enrolled repository can carry up to 20 checks (`/api/merge-checks/repos/<id>/checks`, managed from the web session only), each `off`, `warn` or `block`: a linked issue (optionally open, or carrying a label), a title that starts with one of a list of prefixes or matches a glob of `*` and `?` (never a regular expression), a description that is filled in (a template's HTML comments do not count) and has the named section headings, a size limit in changed files or lines, no unresolved critical ocra finding on the reviewed head, and a check written in plain words. A hosted review of the pull request is given the repository's enabled plain-language checks in its configuration, each under an id made from the check and its text, and uploads whether the change passed or failed each; a check counts the outcome only under the id of its current text, so an edited check waits, saying so, for the next review, as it does when the review could not tell. A review run elsewhere is not given them. The linked issue check waits, saying so, until the review of the head uploads the linked issues it found. Linked issues' titles and labels, and the checks' reasons, are kept only while the account shares findings.

The server evaluates a pull request's checks on its current head when the webhook queues it, when its title or description is edited, and when its review is uploaded, and posts the result as the bot: one check run named `ocra / pre-merge` on GitHub, updated in place when the result changes (the App needs Checks write), or one commit status of that name on GitLab (the bot needs at least the Developer role). A blocking check that fails makes it fail; a failing warning makes it neutral on GitHub and success on GitLab, with the failure in its summary; a blocking check that waits on the review (a linked issue, critical findings, an instruction) keeps it pending (in progress on GitHub) until the head's review lands, unless the repository's pre-merge checks turn off "Wait for the review", when it counts as not evaluated and fails nothing. A head that is never reviewed stays pending, so hold only where reviews run on every push. A result is posted once per head and result. Without a bot, as on Workers, nothing is posted, but the pull request's page still reads the result (`/api/pulls/checks?platform=&repo=&number=`), evaluated as the signed-in user.

## Merge when ready

On a pull request's page the signed-in user can arm "merge when ready" with a merge method (`POST /api/pulls/merge-when-ready` with `platform`, `repo`, `number`, `method`, the `head` they read and optionally `keepOnPush`; `GET` with the same query answers the intent and whether this server can stand in; `DELETE` with `platform`, `repo` and `number` cancels it). Only a web session may. The platform's own auto-merge is used first, as the user: on GitHub, auto-merge (the repository's "Allow auto-merge" setting), armed at the head the user read; on GitLab, merge when the pipeline succeeds (`auto_merge`). It waits on what the platform requires and nothing else: the `ocra / pre-merge` check and a review's critical findings hold it only where branch protection (GitHub) or the project's merge checks (GitLab) require that check to pass.

Where the platform's auto-merge is off, or the pull request could merge already, the server keeps the intent itself, on a repository the same account enrolled (see Auto review) on a server that runs reviews; elsewhere, as on Workers, the answer is `unavailable` and nothing is kept. The intent (one per pull request and account: who armed it, the method, the head, the state and why) is moved by the enrolled repository's webhooks: a pull request's push, edit, review, merge or close, and a finished check suite, check run, commit status or pipeline. It merges, as the user and through the same merge as the page's (which names the head, so a moved one is not merged), once the platform says the pull request is mergeable (required checks and approvals pass, no conflicts), the pre-merge checks are not failing or pending, and ocra's review of the head has no unresolved critical finding. One runner merges it: the database's compare-and-set moves it from armed to merging, and a claim older than five minutes is taken over. A push disarms it unless the user kept it armed on new commits, which moves it to the new head; one armed natively is then turned off on the platform too. Every arming, merge and stop is in the account's audit log, a channel that hears about `merge_when_ready` is told how it ended, and an intent is deleted 30 days after it ended, or 90 days after it was last moved.

The server fallback needs, beyond what auto review needs, the GitHub App's Checks and Commit statuses read permissions and its check suite, check run and status events, besides pull request and pull request review; on GitLab, the project hook's Pipeline events, besides Merge request events. The merge itself is the user's, so their token needs what the page's merge needs: Contents and Pull requests write on GitHub, scope `api` on GitLab.

## Notifications

An account announces its reviews in Slack or WeCom group chats, or to email addresses (`/api/notifications/channels`, at most 10 in all). A chat channel takes the chat's incoming webhook address (`https://hooks.slack.com/services/…` or `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=…`, no other host); an email channel takes one plain address. Either is stored encrypted under `MASTER_KEY` and never answered. Each channel hears about every review, reviews with findings, or only reviews with a critical finding. A message carries the review's counts, verdict, pull request and console links, and the titles of up to three critical or warning findings when the account shares findings. The server needs outbound HTTPS to those hosts. A message that fails is not retried; the channel shows how its last message went, and a test message checks it.

Email needs `SMTP_URL` and `SMTP_FROM`; the hosted Worker has no mailer, so it refuses email channels and `GET /api/notifications/channels` answers `"email": false`. An address gets an email with a link to confirm it, valid for a day (`POST /api/notifications/channels/<id>/confirm` sends a new one; an account sends at most 10 a day), and nothing else until the link is opened and its button pressed. Every email is plain text with a simple HTML part, no images or tracking, and carries an unsubscribe link (also as `List-Unsubscribe`, for a mail client's one-click unsubscribe) that removes the address without signing in. The links are under `<PUBLIC_URL>/api/email/` and the unsubscribe links are signed with `SESSION_SECRET`: changing it invalidates those already sent.

A channel can also hear about the events of the signed-in user's own pull requests on the account's enrolled repositories (`"events"` when added, or with `PATCH`; none unless set, so channels added before keep what they had): `review_requested` (a review was asked of them), `pull_reviewed` (a reviewer approved, requested changes or commented with text on a pull request they wrote; on GitLab, an approval), `pull_closed` (it was merged or closed by someone else), `checks_failed` (its pre-merge checks failed, once per head; on a server with a bot) `review_blocking` (ocra's review of it found a critical finding; that channel then gets this message in place of the review's announcement) and `merge_when_ready` (a pull request they set to merge when ready merged or stopped; see Merge when ready). The user is known by the platform's id of their user, never by a login: on GitHub the account they sign in with, on GitLab the user of the account's GitLab link (a link made before this was kept must be connected again). An event the user caused tells nobody. The webhooks only arrive for enrolled repositories, and are read after they are answered. Each channel is told of an event once: the database keeps its key for 30 days, so a webhook delivered again sends nothing. A message names what happened, the pull request's title and a link to its page in the console under `PUBLIC_URL`; it holds finding titles only when the account shares findings.

A channel set to get the daily digest (`"digest": true` when added, or with `PATCH`) receives, once a day, a summary of the account's reviews of the day before (UTC): how many, of how many pull requests, the counts by severity, the titles of up to five critical or warning findings still open when the account shares findings, and how many of the account's enrolled repositories' pull requests were merged, naming up to five, with links to the console. A day without reviews or merges sends nothing. The server checks every hour and the database records the day sent per account, so several processes on one database send it once. It needs `PUBLIC_URL`, which its links point to.

A channel set to get the weekly report (`"weekly": true` when added, or with `PATCH`) receives, once a week, a summary of the seven days before the account's report slot: a UTC weekday and hour, Monday 09:00 unless changed (`GET` and `PUT /api/notifications/report` with `{"weekday": 0–6, "hour": 0–23}`, Sunday being 0; the answer names the next slot). It holds the reviews and the pull requests they were of, the counts by severity, the findings later runs saw fixed or dismissed, and, when the account shares findings, how many of the week's findings are still open and the titles of up to five critical or warning ones; the pull requests merged, with the median time from opened to merged and the newest five; and the three repositories with the most reviews. A week without reviews or merges sends nothing. A slot is sent within a day after it, or not at all, and the database records the slot sent per account, so several processes send it once and a slot set mid-week waits for its next one. Like the digest, it needs `PUBLIC_URL`; the hosted Worker runs it from an hourly cron.

Merges come from the platforms' webhooks for enrolled repositories (see Auto review): GitHub's pull request `closed` event, through the App's webhook, and GitLab's merge request hook when a merge request is merged or closed. The server keeps one record per pull request (its title, whether it was merged, when it opened and when it closed; a later close after a reopen replaces it) for 90 days, like reviews, and the account's export holds them.

The review flow (`GET /api/insights/flow?days=7|30|90`, optionally `&repo=<full name>` of one enrolled repository) comes from the same webhooks and reads nothing from the platforms. From GitHub's pull request events (opened, ready for review, review requested, reopened, and any other for the title, author, draft state and size) and pull request review events (submitted; the App must subscribe to Pull request review), and from GitLab's merge request hook (open, update with a new reviewer or out of draft, reopen, and approval), the server keeps one record per pull request: its title, author, size where GitHub says it (lines added plus deleted), whether it is a draft, and when it opened, became ready for review, was first asked for a review, first reviewed and first approved, the earliest delivery winning. It also keeps each review once, by reviewer and whether it approved; on GitLab an approval is the review, once per approver. A review by the author or by a bot is not counted. The answer holds pull requests opened and merged per UTC week, the median and 90th percentile from ready for review to the first review and to the first approval and from the first approval to the merge, the five open pull requests waiting longest for a first review, reviews per reviewer, and pull requests opened by size. Pull requests from before a repository was enrolled are not there. Records go 90 days after their last event, reviews 90 days after they were submitted, and the account's export holds both.

## Ask ocra

The review page answers questions about one review and its pull request ("why is this finding critical?", "what does this change do?"): `GET /api/reviews/<id>/chat` reads the conversation, `POST` with `{"message": "…", "model"?: "ocra-<provider>/<model>"}` asks, and `DELETE` clears it. Only a web session asks. A question goes to the model it names, or to the account's standard model (Defaults), or its top or light one when that is unset, and the call is made with the account's own key for that provider, or the server's key for a `MODEL_ENDPOINTS` entry that has one; with none, it is refused (`no_key`). The provider must have an OpenAI-compatible chat route, or else Anthropic's messages route.

Data flow, one question:

1. The server reads what it holds for the review: its counts, verdict and pull request, and, while the account shares findings, the findings' text and the walkthrough (both already redacted on upload). When the account does not share findings the model is told so, and says so when a question needs them. When the account has a connection to the pull request's platform, the pull request's files and diff are read then, as the user, with the same calls as the pull request's page; nothing read is stored. The diff may be of a newer head than the one reviewed, and the prompt says when it is.
2. The prompt holds ocra's instructions, then that data in sections tagged with a random nonce made for the request, so text from the change cannot close a section; any `<ocra` or `</ocra` in the data is defanged as the engine's `data()` does, and control characters are dropped. Each field is cut (findings at 50, a diff at 48,000 characters), the question at 4,000 characters, and the 20 latest messages go with it.
3. The call counts against the gateway's daily cap and the account's budget, in the statement that checks them, and is recorded as a gateway call (provider, path, model, status, tokens, time), as one through `/api/gateway` is. The prompt and the answer are never logged.
4. The answer streams back as server-sent events (`delta`, then `done` with the stored message, or `error`), on Workers and on Node alike, and is cut at 16,000 characters. The question and the answer are stored in `review_chat_messages`; a question that got no answer is removed.

A review keeps at most 100 messages, checked in the statement that adds one; clearing the conversation makes room. The messages are deleted with their review, by the user or after 90 days, with the account, and when the account stops sharing findings and deletes what it shared; the export holds them.
